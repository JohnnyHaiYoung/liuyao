# 第三阶段历法方案决策（Node 部署）

版本：2026-10-04。本文件回答任务书第 5 节：**能否在 Node 部署中可靠完成历法换算**，以及时间/时区/日界/节气的采用口径与证据。相关上游审查见 [phase3_upstream_audit.md](phase3_upstream_audit.md)。

## 1. 结论

**采用 `lunar-typescript@1.8.6`（MIT，零运行时依赖）作为 Node 历法核心，锁定在项目 `paipan/` 模块内**；生产链路**不引入 Python**。Python 侧（`lunar_python 1.4.8`）只保留为**开发期对照**，不作为部署依赖。

必须在自研代码里补足的四件事（都不能依赖上游默认行为）：

1. **严格公历校验**：库对 `2026-02-30` 会**静默溢出**成别的日期（实测见 §4.3），排盘前必须自行做严格日期校验；
2. **月建按节气交接时刻**取值（`getMonthInGanZhiExact()`），不能用按天的 `getMonthInGanZhi()`（实测在该日 00:30 就提前换月，早于交接 19 小时）；
3. **日界策略显式映射**：`midnight → getDayInGanZhiExact2()`、`zi23 → getDayInGanZhiExact()`（语义实测见 §4.2）；
4. **时区白名单**：v1 只接受已验证的 `Asia/Shanghai`，其它 IANA 时区**明确拒绝**（不是回退默认值），时区换算用 Node 自带 ICU。

## 2. 候选调查

| 候选 | 版本 | 许可 | 运行时依赖 | 覆盖范围（实测） | 结论 |
| --- | --- | --- | --- | --- | --- |
| `lunar-typescript` | 1.8.6 | MIT | **无** | 1800-01-01 与 2200-12-31 均有结果 | **采用** |
| `lunar-javascript` | 1.7.7 | MIT | 无 | 未逐项测（同作者同族，体积 512 KB） | 备选 |
| `solarlunar` | 3.1.0 | ISC | 无 | 1899-12-31 / 1900-01-01 无结果，1900-02-01 起正常 | **仅作独立对照**，不作生产依赖 |
| （上游 Python）`lunar_python` | 1.4.8 | MIT | Python 运行时 | 有 1899 结果 | 仅开发期对照 |

选型理由：`lunar-typescript` 零运行时依赖、TypeScript 类型随包、覆盖范围宽、可用 Node 原生能力做时区；`solarlunar` 是**不同作者**的实现，因此其吻合才有独立价值（见 §3.1）。

> **证据强度声明（任务书第 5 节明令）**：`lunar-typescript` 与 `lunar_python` 是**同一位作者（6tail）的同族实现**，两者一致只算**弱证据**，不能互证正确。本决策的独立权重来自：① 包内原书原页印出的干支；② 不同作者的 `solarlunar`；③ 日界/节气/闰日边界与结构性不变量。

## 3. 验证证据

### 3.1 原书原页锚点（"原书原页核对"等级，9/9 通过）

期望值取自阶段 2 包内原件**印刷内容**（人工目视核对过原页）：

| 出处 | 输入 | 期望（原页所印） | `lunar-typescript` 实际 |
| --- | --- | --- | --- |
| PDF `src-e6fc8612e955` 第 2 页 | 农历 1997 八月初七 | 日柱 **癸丑** | 癸丑 ✅（对应公历 1997-09-08） |
| 旧 DOC `src-3f8243c07930` 首页 | 公历 2006-05-10 14:22 | 丙戌年 **癸巳月 己亥日 辛未时** | 丙戌 / 癸巳 / 己亥 / 辛未 ✅（农历四月十三） |
| 扫描件 `src-f3f838d501b1` 第 2 页 | 公历 2003-12-25 09:30 | 癸未年 **甲子月 壬申日 乙巳时** | 癸未 / 甲子 / 壬申 / 乙巳 ✅ |

两组完整的"年月日时"四柱同时命中，说明该实现不只在日柱上可用。

### 3.2 独立实现对照（"独立实现对照"等级）

用**不同作者**的 `solarlunar` 对 9 个日期比对日柱：**7 项一致、2 项为覆盖范围差异**（`solarlunar` 对 1899-12-31、1900-01-01 返回 `undefined`，1900-02-01 起正常）——即**没有发现口径分歧**。测试含闰日 2000-02-29、2024-02-29，均一致。

### 3.3 日界（实测）

```text
2024-01-01 22:30  日柱(默认)=甲子  Exact=甲子  Exact2=甲子
2024-01-01 23:30  日柱(默认)=甲子  Exact=乙丑  Exact2=甲子   ← 两口径在此分叉
2024-01-02 00:30  日柱(默认)=乙丑  Exact=乙丑  Exact2=乙丑
```

结论：`Exact` = 晚子时算明天（**23:00 换日**）；`Exact2` = 晚子时算当天（**00:00 换日**）。本模块默认采用 **23:00 换日（zi23）**，理由：六爻传统以子时起于 23:00，且阶段 2 原书卦例的"晚子时"记录均按次日日柱计；同时把 `midnight` 作为可选口径保留并在盘面中标注，**同一盘不得中途切换**。

### 3.4 节气边界（实测，这是选 Exact 的直接依据）

2026 年立秋交接时刻（库给出）= **2026-08-07 19:42:43**：

```text
2026-08-06 23:30  月柱(按天)=乙未  月柱(按节气时刻)=乙未
2026-08-07 00:30  月柱(按天)=丙申  月柱(按节气时刻)=乙未   ← 按天提前 19 小时换月
2026-08-07 12:00  月柱(按天)=丙申  月柱(按节气时刻)=乙未
```

因此**月建必须按交接时刻**（`getMonthInGanZhiExact()`）。原页锚点 b（2006-05-10）用该口径亦命中。

### 3.5 时区（Node 原生，无 Python）

`Intl.DateTimeFormat` 使用 Node 自带 full ICU：

```text
Asia/Shanghai    -> 2026-08-04 11:17   （UTC 2026-08-04T03:17Z）
America/New_York -> 2026-08-03 23:17
Not/AZone        -> 抛 RangeError
```

v1 时区白名单：**仅 `Asia/Shanghai`**；其它时区返回可识别错误（`unsupported_timezone`），不做静默回退。服务器系统时区**不进入**任何计算（不读 `TZ` 做隐式换算）。

## 4. 已发现的上游陷阱（写入实现约束）

1. **2026-02-30 静默溢出**：`Solar.fromYmd(2026,2,30)` 未报错，被当作别的日期算出"农历 正-十四"。→ 自研入口必须严格校验公历年月日。
2. **月柱按天/按时刻两套结果**（§3.4）→ 只取 Exact。
3. **日界两套结果**（§3.3）→ 显式映射并记录口径。
4. **范围差异**：`solarlunar` 支持范围窄（1900-02 起），`lunar-typescript` 实测 1800–2200 可用；本模块声明**支持范围 1901-01-01 至 2099-12-31**（保守取值，超出即 `out_of_range`），避免把未验证边界当能力。
5. 上游同族互证问题（§2 声明）。

## 5. 部署与打包

- 模块位置：`paipan/`（与聊天应用 `app/` 分离，本阶段**不接入聊天流程**）。
- 依赖：`lunar-typescript@1.8.6`（唯一运行时依赖，零传递依赖）+ 开发期对照 `solarlunar@3.1.0`。
- 锁定：`paipan/package.json` 写精确版本，`paipan/package-lock.json` 锁定树；`.npmrc` 指定 registry 与缓存位置（缓存放项目内，避免宿主缓存目录权限问题）。
- 许可证记录：`lunar-typescript` MIT（`package.json` 内 `license: MIT`，作者 6tail）；`solarlunar` ISC。两者均随 `node_modules` 提供许可文本，采用时把 `LICENSE` 摘录写入 `paipan/THIRD_PARTY_LICENSES.md`（见该文件）。
- 生产链路：**无 Python、无子进程、无网络**。
- 迁移验证：模块不读取 `F:`/`E:` 绝对路径；迁移目录后仅需 `node`（Node ≥ 22）即可运行 CLI（验收时以迁移后的目录复跑）。
