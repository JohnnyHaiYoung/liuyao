# 第五阶段研发任务书：Docker 发布、部署与数据恢复

版本：2026-10-09。交付对象：负责实现的研发 AI。依据：[产品需求](product_requirements.md)、[技术架构](technical_architecture.md)、[研发计划](development_plan.md)、[首版验收清单](acceptance_checklist.md)、[第四阶段独立最终验收](phase4_final_acceptance_d6c5148_2026-10-09.md)。用户已确定目标环境为 **Linux + Docker**。产品/架构方制定要求并独立验收，研发方实现和自测。

## 1. 目标、基线与边界

从第四阶段已签收的软件基线 `d6c5148` 制作一个能搬到 Linux 服务器的**单套私有交付包**：应用、首批 Wiki、六份资料的原件与处理产物、页图、运行所需排盘模块和部署材料一起交付；聊天数据库、备份、日志、密钥在发布包之外持久保存。该包应能在没有开发机 `F:`、`E:` 盘、没有仓库工作区、没有外网包管理器的服务器上导入并启动。交付时记录实际源码提交；`89446a8` 是其后的文档归档提交，不替代第四阶段软件验收基线。

**需要纠正的前提：**“第四阶段本机 `build` 和自动检查通过”不等于 Docker 镜像可运行，也不等于生产库升级或备份能恢复。阶段 2 的资料 ZIP 证明过资料本身可搬迁，不能充当完整应用发布包。构建阶段仍有动态文件追踪提示；提示条数本身不是签收依据，实际镜像内容、运行时读取路径和敏感文件排除结果才是。

本阶段聚焦交付形态与运行保障，不增加断卦规则、批量导入其余资料、微调/向量检索、多用户、多实例或新的占断能力。产品需求中的历史导出与搜索仍为待排期 P1，不在本次发布门槛内；已经验收的聊天、来源和排盘行为不得回退。现实预测命中率不属于软件签收结论。

[Wiki 扩充第一批](wiki_expansion_batch1_spec.md)与本阶段并行研发并独立验收。发布镜像先以已签收的六份来源为稳定基线；新增来源若先通过独立验收，可在明确冻结点纳入同一版本并重做资料、目录与镜像校验。未经验收的清洗产物不得混入正式包。

## 2. 交付形态与部署决策

1. **默认交付形态**：一个版本化的离线交付目录或压缩包，至少含可用 `docker load` 导入的 Linux 镜像、`compose.yaml`、无真实值的配置模板、部署与回滚说明、逐文件/镜像清单及校验值。镜像应包含运行所需代码和已选资料；服务器导入镜像后不再从 Git、npm 或开发机读取文件。允许研发提出等价的 OCI 交付方式，但必须同样做到单套转移、离线导入和独立复验。
2. **目标平台**：先确认服务器 CPU 架构、Docker/Compose 可用性和可用磁盘，再构建相应 Linux 镜像。不得把 Windows `node_modules`、Windows `.next` 或原生模块二进制直接复制进 Linux 镜像。锁文件、Node 运行时版本和镜像基础层须固定并记录；在最终镜像内实际加载 `better-sqlite3`、打开 SQLite、启动应用，以证明原生依赖与目标架构兼容。当前 `app/.npmrc` 的 `ignore-scripts=true` 不可被当作兼容性证明。
3. **应用进程**：沿用单用户、单实例 SQLite 设计。容器内服务可监听容器网络地址，但宿主机端口只绑定 `127.0.0.1`，由宿主机反向代理提供 HTTPS；不能机械照搬非容器部署的“容器内只监听 127.0.0.1”，否则 Docker 端口映射无法访问。Compose 不允许多副本或自动横向扩容。
4. **只读内容与可写数据分离**：镜像中的 `wiki/`、`corpus/`、生产排盘代码、迁移文件为版本化内容；`LIUYAO_PROJECT_ROOT` 明确指向容器内项目根，`LIUYAO_STORAGE_DIR` 指向独立持久化目录。聊天库及 WAL/SHM、备份、日志不得写入镜像层或随发布替换。以非 root 身份运行，并证明数据目录权限、重启和重建容器后的读写都正常。
5. **密钥**：DeepSeek、可选千问及拥有者凭据只从服务器侧受限环境文件或密钥管理注入。真实值不得进入 Git、Docker 构建上下文、构建参数、镜像层、交付压缩包、网页资源、日志或验收截图。生产配置必须关闭假模型；无千问密钥时默认 DeepSeek 仍正常。
6. **反向代理**：沿用现有 nginx 示例中的 HTTPS、Cookie 与 SSE 要求，但要在真实 Docker 端口映射下复核：应用端口不能从公网直连，代理覆盖来源地址头，聊天回复首段在整段生成结束前到达。`LIUYAO_TRUST_PROXY=1` 仅在上述信任链成立后启用。

## 3. 发布包内容与完整性

研发先提交发布包**白名单/排除表**，再实现构建脚本。至少包括 `app/` 运行产物、生产依赖、`app/migrations/`、备份/巡检所需脚本、`wiki/` 及目录、`corpus/manifest.jsonl`、六份已纳入来源链的原件、提取/清洗文本、页图/转写、质量报告，以及项目自身排盘运行代码。`skills/` 只包含审查后实际采用且生产需要的文件；当前生产链路使用项目自有排盘副本，不因目录名叫 Skill 就把四个外部仓库或 `storage/repos/` 一起打包。记录第三方依赖与许可证清单。

必须排除 `storage/` 的现有数据库、备份、测试临时目录、会话记录、`.env.local`/真实密钥、`.git/`、开发缓存、测试报告、旧 `dist/`、Windows 依赖产物及不属于六份样本的私人原件。`corpus/originals/` 虽被 Git 忽略，**仍必须从已核对的本地资料副本显式纳入私有镜像**；不能以 `git clone` 的文件集当作完整包。原件只供容器内受控读取，不增加公开原件下载端点。

生成机器可读发布清单，记录源码提交、目标 OS/架构、镜像 ID 或 digest、Node 与锁文件版本、Wiki 目录哈希、`corpus/manifest.jsonl` 哈希、逐文件路径/大小/SHA-256、排除项检查结果。清单不得把发布归档自己的哈希写回归档内部造成自引用；归档 SHA-256 单独放在交付目录外层或交付记录中。导入前后、解包后逐文件核验；文档、Wiki 与清洗文本的相对链接及 `source_id + ¶NNNN/页码` 必须在交付包内可达。

第四阶段 `next build` 的动态文件追踪提示要有**按最终镜像实物核查**的证据：检查 `.next`、standalone 目录（若采用）、镜像文件系统及镜像层中是否夹带数据库、密钥、临时目录或多余原件；同时确认运行时所需 Wiki/资料没有被错误排除。可以保留有解释且不影响完整性与隐私的构建提示，不能只通过配置排除规则便宣称发布包安全。若选 standalone，须证明静态资源、原生依赖、迁移/运维脚本及外置资料目录在 `docker load` 后都可用；若选 `next start`，须说明其生产依赖和构建产物如何进入镜像，不能把 standalone 问题简单略过。

## 4. 升级、备份与回滚

- 提供可执行的首次部署、更新版本、停机、健康检查、日志查看、备份、恢复和回滚步骤。Compose 配置和脚本必须以独立数据目录为参数，不得因更新镜像清空或重建数据卷；不得使用 `docker compose down -v` 作为常规操作。
- 上线/升级前通过现有 SQLite 在线备份 API 生成一致备份并运行 `integrity_check`；记录迁移版本、会话数、消息数、来源快照数、盘面快照数和代表性历史 ID。备份应能从应用数据卷之外取走；留存天数与异机备份目标由用户在部署时确定。只有同盘同卷的一份备份不能称为灾难恢复。
- 在**正式数据库副本**上先演练新版本启动与迁移、历史回看、来源摘录/页哈希、旧盘快照和标题保留。正式切换时保持单实例，避免新旧版本同时写同一 SQLite 文件；旧镜像与升级前备份须可找回。
- 恢复演练必须在隔离目录完成：停止写入后用已校验备份恢复，处理旧 WAL/SHM，重启并逐项比对。若升级后已写入新消息，回滚旧镜像和旧库会丢失这段数据；发布说明必须写明维护窗口与数据丢失边界，不能把“换回旧镜像”当作完整回滚。
- 自动备份可以新增，但须报告调度、失败告警、留存和异机复制的实际状态；未配置的能力不能写成已运行。

## 5. 研发自测与独立验收场景

研发提供**从实际交付包出发**的一键或分步复验入口，不以开发工作区的成功替代包内结果。所有自动检查写入临时数据卷，不触碰 `storage/liuyao.db`；命令给出退出码、日志位置和实际镜像/归档哈希。

| 场景 | 必须看到的证据 |
| --- | --- |
| 干净环境导入 | 新 Linux Docker 环境仅拿交付包和服务器密钥即可 `docker load`、启动；没有 `F:`/`E:`、Git、npm 安装和开发机路径依赖 |
| 包内完整性 | 逐文件校验、六份原件哈希、Wiki 目录一致性、资料 `verify`、图片与出处定位均通过；包内无私人库/密钥；镜像层检查通过 |
| 原生依赖与首次启动 | 目标架构加载 `better-sqlite3`、迁移成功、`healthz` 和拥有者登录可用；无密钥或无持久化挂载时明确失败而非静默写入容器层 |
| 四条核心流程 | 概念问答、来源比较、完整输入排盘、旧盘追问从网页到历史仍正常；缺项先追问；切模型后立即发送与跨会话切换不串盘/串依据 |
| HTTPS 与 SSE | 宿主机应用端口仅回环可达；公网只能经 HTTPS/登录访问；代理后的流式首段先于结束到达，停止生成仍记录中断 |
| 升级和恢复 | 旧库副本升级后原消息、标题、模型、来源及盘面快照仍在；重启/重建容器不丢数据；已校验备份在隔离目录恢复成功；回滚步骤真实可执行 |
| 上游配置 | 生产假模型关闭；用最小真实请求验证已配置的 DeepSeek 和可选千问（记录费用/是否实际调用）；若暂无可用密钥，明确列为目标环境未验收 |

建议复用第四阶段 `npm run check:all -- --with-http --with-ui`、阶段 2 `verify` 与已有备份脚本，但必须增加**镜像/发布包级**的检查。在镜像里运行浏览器自动化不一定合理；可从包外浏览器访问临时容器。验收方会自行抽取此前脚本未固定的提问、卦例和历史记录。

**签收分两层**：A. 离线交付包在隔离 Linux Docker 环境完整、可启动、可恢复；B. 目标服务器 HTTPS、代理、真实密钥、持久化与备份去向实测。A 通过而 B 未执行时只能标“交付包就绪、目标部署待验收”，不能写“第五阶段最终通过”。

## 6. 交付物与用户待定参数

1. `docs/phase5_release_design.md`：镜像构建策略、目录映射、包清单、原生依赖与追踪提示处理、升级和回滚设计；先提交设计再编码。

3. `docs/phase5_delivery.md`：发布版本、源码提交、镜像/包哈希、逐项自测命令与退出码、部署/升级/备份/恢复/回滚手册、未完成与未验证项。研发自测不写成独立签收。
