# 本地 Wiki 扩充第一批研发任务书

版本：2026-10-09。交付对象：负责资料处理与 Agent 接入的研发 AI。**现在启动，与[第五阶段 Docker 发布](phase5_development_spec.md)并行**；两条工作流各自提交、验收，不把未验收资料混入发布包。依据：[产品需求](product_requirements.md)、[第二阶段资料任务书](phase2_development_spec.md)、[Wiki 编写规则](../wiki/schema.md)、[第四阶段独立验收](phase4_final_acceptance_d6c5148_2026-10-09.md)、[现有资料盘点](corpus_audit.md)。产品/架构方独立验收，不负责批量清洗与编写 Wiki。

## 1. 为什么现在做

当前 `wiki/index.md` 登记 6 份样本来源，聊天已能按 `wiki/catalog.json` 选页，但用户的主要目标是使用 `F:\道教\六爻` 的更多资料。继续只发布六份样本，知识覆盖会明显不足。另一方面，[现有选页代码](../app/src/server/wiki/select.ts)每轮只传少量相关片段；这次只选到两个来源，**不能**被模型说成“Wiki 只录入两个来源”。需要并行修正“资料库存量”和“本次使用证据”的表达。

本批目标是：完成四份候选来源的只读导入与全文提取/清洗，建立可追溯的来源登记和有限、经核对的 Wiki 主张；增加由目录和 manifest 生成的**真实收录范围说明**。不训练或微调模型，不引入 embedding/向量库，不把所有资料一次丢给 LLM，不把来源观点等同于现实预测正确。

## 3. 录入与质量契约

1. 原件只读复制进 `corpus/originals/`，不修改 F 盘；按现有 CLI 的来源身份、哈希、相对路径和去重规则更新 `corpus/manifest.jsonl`。全文提取到 `corpus/extracted/`；清洗成 `corpus/cleaned/` 的 Markdown 时保留稳定段落/章节定位、删改记录、疑字和乱码标记。大讲义允许 Wiki **只覆盖已核对章节**，但“文件已提取全文”和“全部内容已成为可引用规则”必须分开登记。
2. 每份来源提交质量报告：解码方式、章节边界、原件总量、已提取范围、Wiki 已编入范围、开头/中部/末尾及高风险段落抽查、遗漏/错字、作者和版本信息的证据等级。对否定词、卦象/爻位、表格、条件句、应期与现实结果特别核对；未核准段落保持 `needs_review` 或不进入可引用主张。
3. 先建来源页，再为有证据的主题扩写 `wiki/concepts/` 和必要的 `wiki/comparisons/`。每个主张给 `source_id + ¶NNNN/章节`、来源原话的准确摘录或忠实释义、方法标签/未知、适用前提、质量状态。不同来源或方法并列；不能按来源数量投票认定正统，也不能因两个说法表面相似就合并。
4. 更新 `wiki/index.md`、`wiki/log.md`、`wiki/catalog.json`，将标题、别名和主题设置成实际提问可命中的词。新的来源页只有在目录哈希一致、原件/清洗文本可达、定位可靠时才向聊天提供编号证据。保留阶段 2 已有六份来源和阶段 4 聊天行为；资料增加不得覆盖旧消息的引用快照。
5. 本批按首批私有资料处理；不向第三方模型上传整本书。若个别段落需要云端视觉/OCR，先列范围、费用与资料传输风险，未获用户明确同意不调用。不得添加公开原件下载入口。

## 4. “已录入哪些资料”必须按清单回答

新增一个服务端收录范围读取能力，数据只来自 `corpus/manifest.jsonl` 与 `wiki/catalog.json` 的**已核验字段**。实现可为确定性本地回答或向模型提供受控的目录摘要，但最终来源数、文件名、覆盖范围和质量状态须由程序生成，不让模型从本轮 `S1/S2` 反推全库。

对“你录入了哪些资料 / 有多少本书 / 某文件收录了吗 / 这次引用了什么”至少区分四个层次：

| 层次 | 回答含义 |
| --- | --- |
| 已导入原件 | 包内有源文件及哈希，不等于已经提取或读懂 |
| 已提取/清洗 | 声明全文或页段覆盖、质量与待核对范围，不等于已形成 Wiki 规则 |
| 已编入 Wiki | 来源页/概念页中确有可定位主张；说明覆盖主题，不能声称收录了完整古籍 |
| 本次使用的证据 | 只列当前问题实际选中并使用的编号来源；不能用它代表全库总数 |

用户问收录范围时应按真实目录完整列出当前已编入的来源（必要时分页/概览），同时给出新增批次的覆盖状态；问特定文件而目录里没有时说“尚未登记或尚未编入”，不编造“我读过”。每次回答仍保持简明，用户要求时展开明细，末段沿用“最终结果：”。先前回复中“这次主要看到两个来源”可以保留为本次证据说明，但不能写成“本地 Wiki 总共只有两个来源”。

## 5. 与第五阶段并行的发布边界

第五阶段可先以**已独立验收的六份来源**制作候选镜像；本批新增资料和目录在本任务独立验收前不得进入正式发布。若本批先通过，则由第五阶段研发在明确版本冻结点更新镜像清单和哈希，并完整重跑包内校验；不要让镜像中的 Wiki 目录、manifest 与聊天代码来自不同提交。旧会话已保存的摘录/页哈希保持不变，新问题才读取新版 Wiki。

两条工作流同时改动 `wiki/`、`corpus/` 或打包清单时，应各自使用独立分支/工作区并协调合入顺序；不得覆盖彼此的未提交文件。资料的私人原件即使不进 Git，也必须进入对应私有交付包。

## 6. 研发交付与独立验收

研发先提交一页批次设计（来源选择/重复版本、转换方式、Wiki 主题与覆盖、目录问答实现、与 Docker 包的版本边界），再处理资料。交付：四份或经记录替换的原件副本、manifest、提取和清洗文本、质量报告、来源/主题 Wiki 页、目录重建方式、收录范围回答、可重跑的资料包与自测证据，以及 `docs/wiki_expansion_batch1_delivery.md`。报告要分开列出“文件已导入”“文字可读”“条目可引用”“现实预测”，不得把前一项通过写成后一项成立。

验收方至少检查：

1. F 盘原件导入前后哈希不变，包内四份不同哈希、项目内原件和定位链完整；近名 TXT 不被误合并。
2. 每份的全文提取、已编入范围和质量报告一致；长讲义的未核对章节不会被说成已审核规则。
3. 抽查新 Wiki 的两条主张，分别回到原件对应段落；一处不同方法/来源分歧并列而不拼接。
4. 新增词语能由目录选页并在聊天中得到正确编号出处；旧“用神”等入口和历史引用快照不回退。
5. “录入了哪些”“有没有某书”“这次用了哪两份”三类问题得到不同且正确的清单；不再把本轮证据数量冒充总收录数。
6. 把项目/资料包移到无 F 盘的新目录，链接、目录哈希、manifest 与聊天来源接口仍能使用；无密钥、私人库或临时 OCR 缓存泄露。

本任务通过只证明**第一批额外资料的可追溯录入与清单问答正确**，不代表全部 139 份文件、全部古籍或现实占断准确性已完成。
