## 阻断项

### P1-1 清洗 Markdown 的来源链接全部失效

六份 `corpus/cleaned/src-*.md` 的页头都生成 `../sources/<source_id>.md`。从 `corpus/cleaned/` 解析会落到不存在的 `corpus/sources/`；正确目标是项目内 `wiki/sources/`。独立检查得到 **6/6 失效**。生成处在 `tools/corpus-cli.ts:706`。当前 `verify` 只遍历 `wiki/`（约第 935 行），所以其“链接全部有效”的交付结论没有覆盖清洗文本。修复生成路径后，扩展验证范围至 cleaned 页面及其中图片链接。

### P1-2 文字层 PDF 的卦图和图文状态不符合任务书

`src-e6fc8612e955` 的清洗文本 23 页中有 **20 页**出现 `██` 等无法表达阴阳爻的占位字符；其中 18 页没有随包提供对应页图。该来源只保留第 1–2 页 JPEG，却将 **整本 23 页标为 `usable`**；清洗 Markdown 中也没有任何 `![...](...)` 图片引用，扫描 PDF 的 5 页图同样未嵌入清洗页。独立看过文字层 PDF 第 1、3 页：原页确有决定卦例含义的爻位表格，而清洗文本无法还原。任务书第 5、6 节要求影响理解的卦图/表格可在 Markdown 中定位，能辨认的信息另存文字或结构化数据；当前仅写“必要时重跑出图”不能作为随包可用的证据。

修复选择：给实际收录的图表页附包内相对图片链接，并转写或明确标记未辨认的爻位；或者缩小该 PDF 的 `usable` 范围，将未核对图表所在页/段标为 `needs_review`，不作为默认卦例规则。同步修改 manifest、报告、来源页与索引。若扫描件整本页图保留，也应在对应清洗 Markdown 中按页引用并标明来源/页码。

### P1-3 同哈希不同路径的别名会丢失

在隔离目录把同一 TXT 原件复制为 `copy-a.txt`、`copy-b.txt` 并同时加入样本清单后运行 `import`，输出两条导入记录，但 manifest 最终只有一条、`sourceRelativePathFromF=copy-b.txt` 且 `aliasSourcePaths=[]`，`copy-a.txt` 丢失。第 189 行的 `byHash` 只读取命令开始前的 manifest，循环中没有更新；第 214–227 行又以同一 `source_id` 覆盖前一条。交付说明“同哈希只转换一次”没有满足任务书要求的**所有原始路径都要作为别名保留**。修复后用同批和分批导入两种顺序复验。

### P1-4 空提取会被误判为可用

在隔离目录加入零字节 `empty.txt`，运行 `import`、`extract --all`，命令报告 `0 字符（汉字 0）质量=usable`，manifest 状态为 `processed/usable`。`extractTxt` 的质量判定只检查 U+FFFD 数量（第 315 行）；其他格式也应有空正文或异常短页检查。任务书明确要求失败不能生成空白“成功文件”，低质量内容不得升为默认规则。修复后让空/不可读输入成为 `failed` 或 `needs_review`，写入原因与重试信息；`verify` 应识别质量状态与产物不一致。

### P1-5 资料交接尚不是自包含交付

六份原件、全部提取/清洗文本、图片、质量报告及 `corpus/manifest.jsonl` 当前都被 `.gitignore` 排除；`git ls-files corpus` 只列出目录 README。仓库内也没有可复现生成的资料包或打包脚本。当前这台机器的工作目录确实有数据，但**只复制本次提交或克隆仓库会丢失全部阶段 2 资料**。任务书第 8、9 节要求交接包显式包含这些产物。开发方须交付可校验的完整资料包，或可复现的离线打包命令与实际生成物，并列出清单/哈希；不应把文字说明“复制整个项目”当成已经交付。

## 其他内容问题

1. `wiki/sources/src-3f8243c07930.md:10` 写“分片表 1000+ 片”，但 manifest、质量报告均写 **31 片**。应以实际解析结果修正，不能留互相矛盾的技术元数据。
2. `wiki/comparisons/meihua-vs-liuyao.md` 第 3 行称两份材料是“真实分歧/相反立场”，第 15 行又指出一份讨论**起卦**、另一份反对**断卦**混用，“并不存在的冲突”。这是一份有价值的方法边界比较，但现有标题/状态把不同前提说成直接对立。应改为“表面分歧、前提不同”，除非找到同一环节的相反主张。
3. 扫描件质量报告同时写“清洗：段落 14 个”和“段落锚点 183 个”；文字层 PDF 也写“段落 1908 个”和“锚点 1673 个”。若前者是提取器分块数、后者是清洗后的行数，应明确字段定义；否则无法用这些统计判断是否漏页或漏段。
4. 旧 DOC 用自实现解析器提取，抽查报告称“与原件一致”，但提交证据未展示独立渲染或第二种解析方式的对照。当前文本可读，相关主张也可定位；涉及卦盘列对齐时仍应维持待复核范围，不应把自解析与自身输出的比较写成独立原件核验。

## 复验门槛

1. 检查所有 cleaned 与 Wiki 的相对链接、图片链接和来源定位；在无 F 盘的复制目录中打开所引用的 PDF 页图。

3. 在隔离样本上重跑“同哈希两路径”和“空文件/坏文件”案例，并确认 manifest/报告没有假成功。
4. 用实际交接包在另一目录解包；校验文件清单和哈希，不能仅依赖当前工作区中被 Git 忽略的文件。
5. 修正文档内部的片数、段落统计和“直接冲突”表述，再按 `docs/phase2_development_spec.md` 第 9 节逐项报告结果。
