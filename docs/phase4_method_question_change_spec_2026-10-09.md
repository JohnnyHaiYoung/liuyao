# 第四阶段收尾变更需求：纯方法问法只回答方法

- 需求确认日期：2026-10-09
- 基线：`39ff52b`
- 决策人：用户明确选择“纯方法问法只回答方法”
- 性质：第四阶段签收前的产品行为修正；研发完成后由验收方独立复验

## 1. 目标

用户询问六爻的步骤、术语、区别或操作方法时，Agent 应直接回答所问，并按现有规则提供可核对来源。**不得仅因问题中出现“起卦 / 算一卦 / 排一卦”等动作词，就由服务端在回答前附上索取爻值、起卦时间、时区的提示。**

用户明确要求“现在替我起卦 / 排盘”但缺少必要输入时，仍须由服务端本地追问，不调用模型猜测或自动补值。当前盘追问必须继续沿用旧盘快照。这三种行为需分别成立。

## 2. 行为规则与验收样例

| 类别 | 输入样例 | 必须发生 | 不得发生 |
| --- | --- | --- | --- |
| 纯方法问法 | `请问起一卦的步骤是什么`、`算一卦和排一卦有什么区别？`、`我想了解六爻起卦的方法`、`请介绍一下如何用六爻起卦`、`如果要算一卦该怎么操作`、`起卦后该怎么断卦`、`六爻起卦怎么弄`、`占卜怎么弄`、`起个卦怎么操作` | 正常调用模型回答方法；来源按现有机制处理；`chartAction=none` | 本地缺项回复、服务端前置“补六次爻值/时间/时区”提示、`chart` 事件、新盘快照 |
| 明确起新卦，缺输入 | `帮我起一卦`、`请起一卦后解释起卦方法`、`帮我起卦，怎么排`、`请起一卦，告诉我这个卦的应期` | 本地追问六爻值、当地起卦时间、时区；保持 `chartAction=none`，不生成盘 | 把请求仅当知识问法回答、调用模型代填输入、沿用旧盘 |
| 同句先讲方法再明确起卦 | `请介绍起卦方法，然后帮我起一卦` | 按明确起新卦处理；先追问缺项，后续拿到输入再解释 | 因前半句是知识问法而跳过起卦请求 |
| 旧盘追问 | `这卦怎么看`、`这个卦怎么解读`、`这盘如何分析`、`刚才那卦怎么理解` | 有旧盘时 `chartAction=follow_up`，同一快照 ID，不重算；无旧盘时提示补盘 | 当一般方法问题处理、发起新盘、索取一套新卦输入 |
| 学法与代起歧义 | `请教我用六爻起卦` | 只问一句“学习方法，还是现在起卦？” | 在用户选择前直接索取六爻值、时间、时区 |
| 完整起卦输入 | 现有“六爻值 + 起卦时间 + 时区”样例 | 继续由服务端排新盘，盘面与第三阶段 canonical 一致 | 因本次方法问法修复而失去排盘能力 |

“直接回答方法”不禁止模型在解释步骤时自然提到爻值或时间；禁止的是**服务端把它们当成当前问题的缺项，强制向用户索取**。

## 3. 实现约束

1. 调整 `app/src/server/chat/planner.ts` 中 `appendedClarification` 的触发条件。当前 `hasCastAction && 未排盘 && 无完整输入` 覆盖了纯方法问法，不符合本次用户决策。不得通过删掉所有追问来修复。
2. 保持意图优先级：明确新卦动作 → 新卦缺项或排盘；指向当前盘、没有新卦动作且没有完整新输入 → 旧盘追问；学法/代起歧义 → 一句澄清；纯方法/概念 → 正常回答。混合句按实际请求动作判断，不能只凭词表命中。
3. 方法问法的计划对象应满足 `missingInputs=[]`、`appendedClarification=null`、无 `clarificationKind=missing_inputs`、无 `chart` 事件；模型回答及落库历史均不得被服务端前置缺项提示污染。
4. 继续保证缺项时不使用发送时间、服务器时区或模型猜测填充起卦输入；当前盘追问只读历史快照。
5. 不更改第三阶段排盘算法、Wiki 选页、来源校验、模型适配器、SSE 既有事件契约和会话标题能力。

## 4. 回归检查与签收门槛

1. 在计划层给第 2 节各类问法添加**成对断言**：纯方法不附提示；同一动作词处于明确命令时必须追问。不要把“方法回答 + 强制补输入”写成正确预期。
2. 在消息级至少验证一条纯方法问法、一条明确起卦、一条旧盘追问：检查 SSE、模型调用与否、盘面事件、保存后的消息正文与 `chartRunId`。方法问法的流式文本和历史读回均不应含服务端强制缺项提示。
3. 独立复跑 `npm run build`、`npm run typecheck`、`npm run check:all -- --with-http --with-ui` 与 `node tools/corpus-cli.ts verify`。现有 11 类检查均须通过；新增断言应实际覆盖上述正反例。无需为本次文案规则再次调用计费模型 API。
4. 更新 `docs/phase4_delivery.md` 和交接摘要：说明 2026-10-09 用户选择已替代第 9.15 节“方法问法必附提示”的口径；基线提交、断言数量与实际输出一致。不要改写旧提交的历史事实。

## 5. 研发交付

提交代码与回归断言，提供提交哈希、四项检查的实际结果，以及“纯方法 / 明确起卦 / 旧盘追问”各一条消息级证据。研发交付后由验收方复验并给出第四阶段最终签收结论。构建的 20 条动态追踪提示与 standalone 发布包核验仍归第五阶段，不因本次变更扩大范围。
