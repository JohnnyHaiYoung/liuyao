# 个人六爻 Agent 研发计划

版本：2026-10-01。本文是项目主路线图。开发方按 [产品需求](product_requirements.md) 和 [技术架构](technical_architecture.md) 实施，交付后按 [验收清单](acceptance_checklist.md) 核查。资料格式与转换细节见 [资料处理旧草案](implementation_plan.md)，已有盘点见 [资料盘点](corpus_audit.md) 与 [首批资料抽查](pilot_source_assessment.md)。本项目的需求、架构和验收由产品/架构方负责；编码与部署由其他开发 AI 完成。

## 目标与判断

做一个可随项目资料一起打包到服务器的个人 Agent。它能回答六爻概念问题、比较不同来源的说法，并在输入足够时用本地程序排盘，再给出简明分析；用户要求时展开依据，回答最后给出「最终结果」。主模型使用 DeepSeek 官方 API 的 `deepseek-flash`，复杂问题可切换到阿里云百炼的 `qwen3.7-plus`。暂不需要 embedding 服务。

**必须区分三种正确性：**原文是否被准确提取和引用、排盘是否按声明的口径算对、某种占断是否能预测现实。前两项可以逐步核查；第三项不能因书籍、Skill 或模型意见一致就认定成立。用户尚未读过这些书，因此系统要展示依据与不确定性，不能把“人工复核”默认为用户已完成。

当前已有目录骨架、139 份文件的初步盘点、少量文本抽查和一个 Wiki 试点页。**尚未批量导入、完成 OCR、实现排盘或接通 API。**首版先证明一个小资料集的完整流程可用，再决定批量处理的顺序。

## 首版交付范围

首版完成后，用户应能在个人网页中：

1. 用自然语言问术语、规则、某来源的观点；回答能定位到项目内的来源和页码、章节或段落。
2. 问“不同书怎么讲”时看到并列观点、适用条件和冲突，不把多套方法合成一条虚构规则。
3. 提供完整的六爻输入后得到本地程序生成的盘面和分层解释；缺少关键输入时只追问必要信息。
4. 默认收到短答；需要时能查看详细依据和计算口径；最后一段始终是「最终结果」。
5. 新建、恢复和继续历史聊天，在当前聊天页或历史列表重命名同一会话标题；模型回复逐步显示，重启服务后历史仍在。
6. 把完整项目包搬到服务器后，脱离开发机的 `F:`、`E:` 路径仍能运行并查到出处。

首版优先覆盖一批有代表性的资料和一种明确的排盘口径。更多书籍、更多断法与界面优化按质量反馈逐步增加。初期“自由问答”指能在**已整理内容的范围内**自由提问，不能承诺已覆盖全部 139 份文件。

## 技术结构与数据契约

```text
离线：F 盘只读原件 → 项目内原件副本 → 提取/OCR → 清洗 Markdown
                                             ↓
                               来源登记 → Wiki 页面与索引

在线：问题 → 识别任务与必需输入 → 按目录读取相关 Wiki 页面
                           ↘ 本地排盘工具 ↗
               问题 + 选中页面 + 计算结果 → LLM API → 回答与出处
```

| 部分 | 首版方案 | 关键约束 |
| --- | --- | --- |
| 服务与入口 | Node.js/TypeScript + Next.js，自托管网页和 API | 一套应用提供自由聊天、历史列表、会话标题重命名和私人访问；依赖锁定并在服务器重建 |
| 实时回复 | `POST` 返回 SSE 格式的流；浏览器用 `fetch` 读取 | 只用于 AI 逐步回答；历史列表与重命名走普通 JSON 请求；停止生成要保留中断状态 |
| 会话存储 | SQLite 文件放在持久化 `storage/`，使用版本化迁移 | 个人、单实例足够；暂不要求用户安装 PostgreSQL；未来多用户/多实例再迁移 |
| 模型 | DeepSeek Flash 为默认；千问 `qwen3.7-plus` 为可选复核/复杂分析模型 | 两家各自的 API Key 由服务器环境提供；逐次记录模型、提示版本和费用相关用量 |
| 知识读取 | 从 `wiki/index.md` 出发，按主题、标签和页面链接选择页面；必要时打开对应的清洗文本 | 只送与当前问题有关的内容和图片；保留来源定位；无向量数据库 |
| 原始资料 | `corpus/originals/`、`extracted/`、`cleaned/`、`assets/` 加 `manifest.jsonl` | 用项目相对路径、SHA-256 和页/段定位串起原件到 Wiki 的链条 |
| 排盘 | TypeScript 适配器优先评估现有 JavaScript 核心，历法模块独立选型；与模型解读分离 | 固定输入方向、六次爻值、时间/时区及历法与规则版本；输出结构化盘面 |
| 本地 Skill | 对选中的第三方 Skill 下载固定版本，审查后把采用部分放入项目并写 TypeScript 适配器 | 两个排盘候选的上游都含 Python 依赖；若生产直接调用 Python，必须把运行时和依赖一起打包并记录理由 |
| 图片 | Markdown 中用项目相对路径引用；需要识图时由服务显式读取并提交相关图片 | 图中的爻位、文字和表格尽量同时保存为结构化文本；扫描页优先评估 OCR 质量 |
| 发布 | 单目录发布包，包含 Node 应用、依赖说明、Wiki、已采用 Skill、原件与处理产物 | 密钥不入包；聊天数据库、备份和日志保存在持久化 `storage/`，升级时保留 |

这里的“按目录读取 Wiki”仍然是运行时使用外部知识，但没有使用向量相似度检索。页面选择先用显式索引和主题标签；当 Wiki 增大、目录导航出现明显漏读时，再评估本地全文索引。长上下文不等于每次把全部资料发给模型。

## 开发顺序与阶段验收

| 阶段 | 具体工作与交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| **0. 需求与架构（已完成）** | 产品需求、Node 架构、Skill 集成原则与验收清单 | 开发方能据此拆分任务；含糊项先记录假设 |
| **1. 网站基础闭环** | 按[第一阶段研发任务书](phase1_development_spec.md)实现 Next.js 网页、单用户访问、SQLite 会话存储、历史列表及当前聊天页的标题重命名、DeepSeek 流式聊天 | 能自由聊天、停止生成、两处改名同步、刷新后继续历史；服务重启后聊天仍在；SSE 在目标代理后仍逐步显示 |
| **2. 资料小样本与 Wiki** | 选至少 6 份代表性资料，涵盖 TXT、DOCX、旧 DOC、可提字 PDF、扫描 PDF；复制原件，生成 manifest、清洗 Markdown、图片和质量报告；编写有出处的首批 Wiki 页 | 每条可用规则能定位回包内原件；失败/乱码有状态；冲突来源分开；F 盘未被修改 |
| **3. Skill 审查与排盘** | 获取两个真正的 Skill 仓库固定版本，审查许可/依赖/输入输出；优先评估 `liuyao-skills` 的 JavaScript 排盘核心，用 `fortune-liuyao-skill` 独立对照；单独确定 Node 历法实现 | 相同输入重复得到同一盘面；已实现字段可独立核对；日界、时区和节气边界有口径记录；生产依赖清单与发布包一致 |
| **4. Agent 融合** | 将 Wiki 阅读器、排盘、会话上下文、DeepSeek/千问适配器接入同一聊天流程；展示来源和盘面快照 | 概念问答、来源比较、具体卦例和后续追问均能走通；模型切换不改 Wiki；旧记录保持原貌 |
| **5. 验收与发布** | 开发方提交固定问答/排盘样例、完整发布包、备份恢复及启动说明；按验收清单核查 | 发布包链接和 manifest 有效，密钥不入包；脱离 F 盘可运行；历史数据升级后保留 |
| **6. 扩充与优化** | 按使用频率和提取质量逐批处理余下来源；必要时改进 OCR、导航和历史管理 | 每批资料经过相同追溯和质量门槛，不能因文件转换成功就自动成为规则 |

**交给开发 AI 的第一项工作**是阶段 1：建立可持久保存的自由聊天网站。资料处理可在网站基础闭环后推进；现有短文试点可供阶段 2 使用，不必等待所有扫描书处理完。

## 模型调用与评估办法

- **普通问题：**Agent 读取 Wiki 索引及少量相关页面，调用 DeepSeek Flash。选中的页面和来源 ID 随回答记录，用户可要求展开。
- **复杂比较：**当来源分歧多、图片难辨或用户要求第二种分析时，可用 `qwen3.7-plus` 复核。切换是产品策略，不预设其六爻结论更准确。千问官方文档列出该模型的文本、图像输入、工具调用和结构化输出能力：[模型说明](https://help.aliyun.com/zh/model-studio/qwen3-7-plus)。
- **扫描页：**先比较本地 OCR 在代表性页面上的表现；如卦象、表格或手写内容识别差，再小范围试用专门的 `qwen3.5-ocr`。它是资料处理候选，不是日常解卦主模型：[视觉模型说明](https://help.aliyun.com/zh/model-studio/vision-model/)。
- **费用控制：**限制单次选页、图片数量和输出长度；缓存可复用的清洗与 Wiki 结果；记录每次模型用量。实际费用随模型、地区和输入长度变化，上线前根据真实问题测量。

先建立一组固定评估问题，覆盖概念解释、跨来源比较、完整卦例与缺少输入的情况。检查“引文能否回到原件”“计算是否与确定性工具一致”“是否混淆体系”“是否按要求短答并在末尾给最终结果”。这组问题衡量软件和资料处理质量；**不把现实事件的预测命中率当作已验证指标**。如果后续发现模型稳定地犯某类格式或步骤错误，再讨论微调；原书全文不能直接代替经核对的训练样例。

## 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 旧 DOC、扫描 PDF 多，自动提取容易漏字、错序或误识卦图 | 小样本先行；逐页记录质量；保留原页图与人工可复核位置；低质量内容暂不提升为 Wiki 规则 |
| 多种方法借用同一术语，规则可能互相冲突 | 来源页保留原说法；方法标签有证据才确定；回答并列分歧与适用前提 |
| 模型可能编造出处或把计算交给自然语言推断 | 出处由程序提供候选和路径；盘面由本地模块生成；回答时核对引用与实际打开的页面 |
| 第三方仓库的实现、版本及许可不一致 | 固定提交版本，检查许可与依赖，先同输入比对，再决定复用范围 |
| 资料和私人问题会发往第三方 API | 每次只发送必要片段；避免在提示中带入整本书或无关个人信息；部署时限制访问并妥善保存密钥；原件包只供私人部署，不开放资料下载入口 |
| 打包体积和服务器环境未知 | 发布包显式包含原件和产物，并用相对路径；是否容器化在获知服务器系统后确定，不阻塞前四阶段 |

## 当前需要用户提供的内容

现在不需要用户阅读 139 份书、下载 Skill 或安装 PostgreSQL。阶段 1 联调时需要 DeepSeek API Key；启用第二模型时才需要阿里云百炼 API Key，密钥只放在服务器环境中。阶段 5 前需知道服务器系统及容器条件；在此之前按单用户自托管 Node 服务、持久化 SQLite 设计。资料分类、样本选择和初步质量复核由开发流程承担。需求、架构和验收由本项目产品/架构方负责，具体编码由用户指定的其他 AI 完成。
