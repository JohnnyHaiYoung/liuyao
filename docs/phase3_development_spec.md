# 第三阶段研发任务书：Skill 审查、历法口径与确定性排盘

版本：2026-10-04。交付对象：负责实现的研发 AI。本任务书细化[研发计划](development_plan.md)阶段 3；[产品需求](product_requirements.md)、[技术架构](technical_architecture.md)与[第二阶段验收结论](phase2_reacceptance_18bcb3b_2026-10-04.md)是输入。产品/架构方负责独立验收，研发方负责下载、审查、编码和验证。

## 1. 目标与边界

交付一个**不调用 LLM**、输入相同即可复现的本地排盘模块。它接收六次爻值和明确的时间口径，输出可保存的结构化盘面；对缺少或不可靠的历法字段给出明确的不可用状态，不能猜填。第三方 Skill 只作为候选实现和方法来源，不能因为仓库自称“完整”或有测试就直接视为正确。

本阶段不把排盘接入聊天、DeepSeek、Wiki 自动选页或历史数据库；这些属于阶段 4。也不批量扩充原书、实现占断预测、安装全局 Agent Skill、加入 embedding/RAG，或改变阶段 1、2 已通过的行为。允许新增独立命令行入口供开发与验收调用。

**关键判断：**排盘的可核对性，与现实预测是否准确是两回事。两套程序输出一致也只能说明实现一致，不能替代可追溯的规则来源或人工核对的样例。

## 2. 候选仓库的审查顺序

用户给的四个仓库中，本阶段只获取两套实际有排盘代码的候选：[songgoldenwind-crypto/liuyao-skills](https://github.com/songgoldenwind-crypto/liuyao-skills) 与 [shubhaviatiningsih-byte/fortune-liuyao-skill](https://github.com/shubhaviatiningsih-byte/fortune-liuyao-skill)。前者当前公开 README 把 `liuyao-paipan-code` 的 JavaScript 排盘与 Python 历法桥接分开说明；后者当前公开 README 说明 Python 3.10+ 和内置 `lunar_python`。这些是**上游自述，尚非本项目审计结论**。审查应以下载后固定的具体提交为准，不跟随浮动 `main`。[前者排盘模块说明](https://github.com/songgoldenwind-crypto/liuyao-skills/blob/main/liuyao-paipan-code/README.md)、[后者仓库说明](https://github.com/shubhaviatiningsih-byte/fortune-liuyao-skill)。

1. 把两仓库的**完整提交 SHA**、获取日期、来源 URL、文件哈希、许可证和传递依赖记录在审查报告；审查用快照留在 `storage/` 下的隔离目录。先阅读代码及安装脚本，再执行任何第三方命令。不得把上游仓库一键安装到用户全局 Agent 目录。
2. 审查输入顺序、爻值定义、起卦方式、历法依赖、日界、节气、输出字段、异常行为、文件/网络/子进程调用，以及代码/数据/素材各自的许可。上游测试结果只作线索，本项目重新执行并核对核心样例。
3. 优先评估 `liuyao-paipan-code` 的 JavaScript **排盘核心**是否能在本项目 Node 进程中复用；将其 Python 历法桥接视为单独候选，不能因核心是 JavaScript 就宣称生产链路“纯 Node”。用 `fortune-liuyao-skill` 的 Python 核心做同输入对照，并记录双方不同的规则前提。
4. 只有实际采用的源码、必要数据与许可文件才进入项目 `skills/` 和将来的发布包；未采用的评估快照不进生产依赖。保留 MIT、Apache-2.0 及其传递依赖的版权和许可记录。另两个仓库仍按[外部仓库评估](external_repositories.md)作为知识或界面参考，本阶段不复制其代码。
5. 对两套 Skill 的**排盘事实**与**解读方法**分别登记。尤其 `liuyao-skills` 的两种解读 Skill 自述有方法边界，本阶段不得混成单一“权威算法”。

## 3. 输入契约与默认口径

| 项目 | 本阶段要求 |
| --- | --- |
| 六次爻值 | 恰好六个 `6/7/8/9`，**第一个为初爻，最后一个为上爻**；`6/9` 为动爻。入参与回显都标明此顺序，不能悄悄倒序。 |
| 手动硬币记录 | 若接受三枚硬币原始结果，必须回显正反面约定及六次到爻值的换算；不同约定不可混用。最小可用入口是直接提供六个爻值，不以自动随机起卦作为验收捷径。 |
| 时间 | **自动历法模式**保存原始起卦时刻、IANA 时区、换算后的当地民用时间及日界口径。首版至少可靠支持 `Asia/Shanghai`；其他时区若未验证，应明确拒绝。服务器系统时区不能成为隐式输入。 |
| 历法模式 | 同时允许**显式提供已知日柱/月建**作排盘核心对照（可不提供时刻，但要标明 `manual_calendar`），以及**由时刻计算历法上下文**的生产路径（必须提供时刻和时区）；两条路径必须区分来源，不得用用户提供的日柱冒充自动计算。 |
| 日界 | 研究并声明所选默认口径；至少比较午夜换日与 23:00 换日，记录边界样例和选择理由。不能在同一旧盘的后续计算中切换。 |
| 月建/节气 | 明确是否按节令“节”划分月建、所用时区和节气数据来源；节气前后必须有可核对的边界样例。农历月、民用月和节令月不得混为一个字段。 |
| 缺项 | 缺少日柱/月建或历法计算失败时，只输出独立可算的字段；六神、旬空、月建相关字段应为 `unavailable`/`null` 并附原因，不得展示上游默认值为真实盘面。 |

研发方须形成版本化的**规则口径文件**，列出爻值、阴阳/动变、八宫、世应、纳甲、六亲、六神、伏神、旬空的采用规则、适用条件与核对来源。能从第二阶段包内原件定位的，记录 `source_id` 与页/段；不能独立追溯的，明确标为“第三方实现规则”，不要伪称古籍原文或传统共识。若上游对某字段采用不同算法，应保留差异表并提出首版选择理由，不作无依据投票。

## 4. 模块边界与输出契约

实现上把三层分开：

```text
六次爻值 + 时间/时区/日界
       ↓ 输入校验与规范化
历法适配器 → 已知或算得的日柱、月建、节气证据
       ↓
版本化排盘核心 → 结构化盘面 JSON → 文本展示/未来 Agent 接口
```

盘面 JSON 至少包含：原始输入及其顺序、输入模式、时区与日界、历法结果及来源/版本、本卦和变卦、卦宫及世应、六爻逐行的阴阳与动符、已实现的纳甲/六亲/六神/伏神/旬空字段、缺项及原因、规则版本、排盘核心版本和采用的上游提交。逐行显示可以从上到下，但必须保留原始输入的初爻到上爻顺序，避免界面层重排污染计算。

排盘核心不得调用 LLM、读取聊天历史或擅自访问网络；文本展示只读结构化盘面，不能另算另一套盘。相同规范化输入、历法和规则版本应得到相同的盘面内容；运行时间戳等审计元数据不得混入盘面等价比较。非法爻值、错序标记，以及**自动历法模式下**缺失时区、无效日期或超出历法支持范围，均应返回可识别错误；手动历法模式缺少某字段时按“缺项”规则降级，不能返回“看似完整”的默认盘。

## 5. Node 历法方案的决策门槛

项目上位架构要求生产问答服务以 Node.js/TypeScript 为主，**不预设 Python 运行时**。研发方需调查可在 Node 部署的历法实现，提交候选版本、许可证、依赖与支持日期范围，并用独立来源或可人工核对的历法/节气样例比对。重点检查 `Asia/Shanghai`、23:00、00:00、节气交接前后、闰日、无效日期，以及服务器位于不同时区的情况。

若找到可靠的 Node 方案，写明其准确性证据、已知限制和锁定版本，再接入本项目；不要只用上游同一库生成的期望值验证该库自己。若暂不能可靠完成，请提交**架构差异提案**：明确 Python 辅助服务或手工日柱/月建模式的能力、部署成本、打包依赖、失败行为及仍未通过的验收项，交由产品/架构方复核；不能静默把 Python 子进程放进生产链路，也不能把“仅能手工输入历法”写成自动排盘已完成。

## 6. 验证样例与异常场景

开发方提交固定输入、预期关键字段、核对依据与实际输出的样例集，至少覆盖：六爻皆静、老阴动、老阳动、多动爻、本变卦和世应、伏神/旬空需要显示与不显示、缺少日柱/月建、午夜与 23:00 两种日界、节气边界、非法爻值及无效日期。对于每个字段，说明是原页人工核对、独立程序对照、领域规则推导，还是仅与上游自测一致；不要把这些证据等级写成同一层。

结构性不变量可覆盖全部 `4^6 = 4096` 种六爻值组合及 64 个本卦编码；这能找出程序自相矛盾、漏卦和倒序，**不能单独证明纳甲等传统规则正确**。抽样的原书卦例要目视核对包内原页图，避开第二阶段标为 `needs_review` 的疑点字与未逐格复核处，或如实标记其不适合当金标准。两套上游实现有分歧时列出具体字段、输入、版本和可能的口径原因，不静默取其一。

独立验收将使用开发方未写入样例集的新输入复算，检查稳定性、跨实现差异、历法边界、错误路径和发布目录迁移。研发方必须给出可复制的命令行或模块入口，使验收者无须运行聊天模型即可取得 JSON 盘面。

## 7. 交付物与验收门槛

1. `docs/phase3_upstream_audit.md`：两个候选仓库的固定完整 SHA、许可/依赖/行为审查、复用范围及弃用理由；两种解读方法的边界单列。
2. `docs/phase3_rule_profile.md` 与机器可读规则版本：字段定义、来源定位、默认选择、差异和未核实点。
3. `docs/phase3_calendar_decision.md`：Node 历法候选和决定、时间/时区/日界/节气口径、支持范围与边界证据；若未达标，提供架构差异提案而非虚报完成。
4. 本地 TypeScript/JavaScript 排盘模块、输入/输出类型、命令行入口、必要的采用源码与许可文件；采用代码应在项目 `skills/` 有固定版本记录，运行不依赖开发机绝对路径。
5. 固定样例、差异表、实际输出及独立核对材料；错误输入和缺项行为可重跑。
6. `docs/phase3_delivery.md`：启动/复跑说明、生产依赖清单、已实现与未实现字段、包内文件清单与哈希、迁移目录后的运行证据。保留阶段 1 聊天与阶段 2 资料，不把新模块偷偷接入聊天流程。

**通过条件：**第三方代码许可和版本可审计；生产依赖与部署说明一致；六爻输入、排盘事实和历法边界可独立复核；错误/缺项不伪造字段；包内模块脱离 `F:`、`E:` 可复现；阶段 1、2 已通过的功能与资料未被破坏。现实占断命中率不作为本阶段正确性证明。
