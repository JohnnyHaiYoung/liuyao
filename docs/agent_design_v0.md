# 个人六爻 Agent 设计草案

状态：2026-09-30 早期讨论稿。当前开发依据 [产品需求](product_requirements.md)、[技术架构](technical_architecture.md) 与 [研发计划](development_plan.md)；本文保留知识组织与方法边界思路。用户已确认允许 Agent 在回答时按目录读取本地 Wiki。目标是接入第三方 LLM API 的个人 Agent；不用向量数据库或 embedding RAG。这里的「LLM Wiki」指先把资料整理为可维护的 Markdown 知识页，再由 Agent 按目录阅读。首个 Wiki 样板见 [wiki/index.md](../wiki/index.md)。

本地资料盘点见 [corpus_audit.md](corpus_audit.md)，首批正文抽查见 [pilot_source_assessment.md](pilot_source_assessment.md)，四个外部仓库的角色见 [external_repositories.md](external_repositories.md)。分阶段实施与技术选择见 [implementation_plan.md](implementation_plan.md)。这些盘点尚未证明资料内容正确或已划分出可靠流派。

## 先明确几个不同的东西

| 部分 | 实际作用 | 是否让模型「学会整本书」 |
| --- | --- | --- |
| 原始资料与清洗文本 | 保存证据、版本、章节位置和提取质量 | 否 |
| LLM Wiki | 离线综合术语、规则、案例和体系分歧；运行时按索引读取知识页 | 否。它是外部知识，不改变模型参数 |
| Skill / Agent 指令 | 规定补问、排盘、比较体系、呈现依据和回答格式 | 否 |
| 排盘程序 | 对明确输入做历法、卦象及其他可确定的计算 | 否 |
| 监督微调 | 用审过的问答样例训练回答步骤、方法选择、措辞和格式 | 可能吸收部分知识，但不能当作完整、可溯源的书库 |

「自由回答」应理解为不受固定问题模板限制，可以就六爻概念、规则、案例、体系差异和具体卦例对话；不能承诺无输入也能推出具体卦象，或保证占断结论准确。

## 推荐结构：第三方 LLM API + 本地 Wiki + 排盘程序

```text
离线建库：原始文件 → 文本提取/OCR → 来源登记 → 分来源摘要
                                         ↓
                         术语页 / 规则页 / 体系页 / 分歧页 / 案例页
                                         ↓
                                   Wiki 索引与维护记录

在线问答：自然语言问题 → 判断问题类型与缺失信息 → 必要时调用排盘程序
                                   ↓
                        读取 Wiki 索引和选中的知识页
                                   ↓
                     把问题、排盘数据和知识页交给第三方 LLM API
                                   ↓
                        简明分析 → 按需展开依据 → 最终结果
```

客户端自己负责文件读取、组装上下文和调用 API，因此不要求服务商提供文件搜索或原生工具调用。选择 Wiki 页面可以先用目录、标题、标签及明确的页面链接；不用向量索引。**这仍是运行时读取外部资料**，只是不同于按相似度取原文切块的常见 RAG。若用户要排除任何运行时资料读取，则不能采用这个在线流程。

Wiki 的价值是把多本书的相同概念、适用条件和冲突提前梳理好，避免每次问答从零比较原文。代价是初次整理、OCR、交叉核对和日后维护都需要时间及 API 调用。它并不会因改名为 Wiki 就自动消除遗漏或幻觉。

## Wiki 内容约束

1. 原始文件只读；清洗文本保留到原文件和页码、章节或可复核片段的映射。OCR 和乱码内容标记提取质量。
2. 每条可用规则记录：原文出处、版本、体系归属的依据、适用条件、例外、与其他说法的关系。出处不明时标为「待核对」。
3. 同一概念可以有多套解释。分别保存各来源观点、分歧原因和案例，不把不同流派的规则混成一套，也不靠来源数量投票。
4. 建立 `index.md` 作为主题目录，另存来源页、概念页、体系页、对照页和案例页；每次新增来源后更新受影响页面与维护记录。
5. 对 Wiki 页定期检查孤立页面、失效出处、矛盾和缺口。Agent 可以提出修改，但不把未经核对的推断自动升为权威规则。

建议先只编译少量可读资料和一两个清晰问题类型，观察引用是否能回到原文，再扩展到全部书籍。当前盘点中存在扫描 PDF、旧版 DOC、重复与质量不一的文本；批量直接交给模型会把提取错误一起写进 Wiki。

## 微调放在何处

首版先用现成模型、短的核心指令和 Wiki。等真实问答积累了经过核对的样例，再看是否需要微调。适合微调的训练样例包括：何时补问、如何选择或并列比较体系、怎样承认资料冲突、怎样调用排盘结果，以及「简明分析，必要时展开依据，最终结果放末尾」的回答风格。

不建议把尚未阅读和核对的 139 个文件直接转成训练语料。理由是：原文不等于高质量监督样例；各书规则可能冲突；有 OCR 和版本错误；微调后很难知道某句话来自哪一页，也无法简单修订单条规则。训练支持、格式、价格和数据保留政策取决于最终选定的 API 服务商，选型时再核实。

如果完全禁止在线读取 Wiki，可选方案是把有限的、人工或程序核对过的核心规则常驻提示词，再用微调样例固定分析流程。这种方案只能覆盖压缩后的规则集；较长资料不能保证被模型稳定记住或正确引用，新增资料通常需要重新整理训练数据、重新训练。需要根据实际问答覆盖率决定是否能接受。

## 一次咨询如何工作

1. 判别是概念解释、流派比较、书中观点追问，还是具体卦例。具体卦例仅补问排盘必需的数据。
2. 对同一份原始输入调用确定性排盘程序；记录时区、时间口径和采用的计算规则。不同方法若口径不同，分别计算。
3. 由客户端读取 Wiki 目录、相关体系页和规则页，限制送入 API 的资料范围，并保留出处标识。
4. LLM 逐体系给出解释，明确区分「用户提供的事实」「程序计算」「书中说法」「综合推测」。影响结论的分歧才进入默认短答。
5. 默认顺序：问题与卦象摘要 → 关键分析 → 必要的体系分歧 → **最终结果**。用户要求时再展开排盘、规则、原文位置和其他体系解释；依据不足时在最终结果明确说无法判断。

占断解释不当成可验证的现实事实。医疗、法律、财务等高影响问题应按现实证据做决定，Agent 可以说明传统说法，但不能替代专业判断。

## 四个外部仓库的位置

- `woaichiji/liuyao`：可作为术语与主题线索，核对出处后才编入 Wiki。
- `fortune-liuyao-skill`、`liuyao-skills`：主要作为排盘代码、方法边界和工作流候选；Skill 内容是过程约束，不等于训练完成的模型。
- `divination-liuyao`：主要作为界面和另一种卦辞叙事方式的参考，不预设它与纳甲六爻属于同一套规则。

本地安装 Skill 只会提供说明文件和脚本。自建 Agent 需要显式登记 Skill 路径、读取说明、选择何时调用，以及把可执行脚本包装成受控工具；第三方 LLM API 不会自动发现电脑上的 Skill。优先将排盘能力作为独立工具接入，解读指令按方法分别保存，避免互相覆盖。

代码、文章与原始书籍分别登记版本和许可；第三方实现自称正确的计算结果仍需同输入核对。详见 [external_repositories.md](external_repositories.md)。

## 建设顺序

1. 固定目标：做一个可整体部署到服务器的个人 Agent，接一个可配置的第三方 LLM API；按用户确认，允许回答时按目录读取同包 Wiki，运行时不依赖开发机 F 盘。
2. 选少量可读来源做 Wiki 样板，先建立来源、术语、规则、体系差异和引用格式；扫描页先处理提取质量。
3. 做排盘模块与问答主流程，让概念问答和具体卦例都能工作。接入外部仓库之前先核对代码接口与时间规则。
4. 用真实问题审阅回答与出处，记录哪类错误来自文本、Wiki、计算或模型；据此扩充 Wiki 或修正 Skill。
5. 只有反复出现稳定的流程或格式错误、且已有足够审过的样例时，再比较微调是否带来改进。

已经确认按目录读取同包 Wiki。项目内还须包含原件副本、清洗文本、Skill 和程序，详见 [implementation_plan.md](implementation_plan.md)。第一版已确定使用 DeepSeek 官方 API 的 `deepseek-flash`；资料整理与排盘模块可以先独立推进。
