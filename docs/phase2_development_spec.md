# 第二阶段研发任务书：小样本资料库与可追溯 Wiki

版本：2026-10-02。交付对象：负责编码与资料处理的开发 AI。本任务书细化[研发计划](development_plan.md)的阶段 2；[产品需求](product_requirements.md)、[技术架构](technical_architecture.md)和[Wiki 编写规则](../wiki/schema.md)是上位约束。产品/架构方负责验收，不承担本阶段开发。

## 1. 目标与边界

把 `F:\道教\六爻` 中**至少 6 份有代表性的文件**做成可随项目一起搬到服务器的资料小样本：项目内原件副本、可定位的提取文本、清洗后的 Markdown、必要图片、机器可读的来源登记、逐份质量报告，以及有出处的 Wiki 页面。用户没有读过这些书，因此不能把自动提取成功等同于内容准确，也不能要求用户先替开发方校对全书。

本阶段交付的是**离线资料与知识组织能力**。不接入聊天页面或 DeepSeek，不实现 Agent 自动选页、排盘、第三方 Skill、向量检索或 embedding；这些分别属于后续阶段。阶段 1 的聊天功能应保持可用，不能暗示已读取新资料。现有 [Wiki 试点](../wiki/index.md)要与新产物对齐，不得静默删改其来源判断。

## 2. 样本范围与选择

至少包含 2 份 TXT、1 份 DOCX、1 份旧 DOC、1 份有实质文字层的 PDF、1 份扫描或图片型 PDF，共至少 6 个**不同哈希**的来源。样本要同时覆盖术语/规则、不同方法的边界和至少一个可由两份来源讨论的共同主题。选择依据须记录正文抽查结果，不能只看文件名。

以下是根据[现有盘点](corpus_audit.md)提出的**候选**，不是对内容、作者或质量的预先认定；若抽查发现不合适，换同类型文件并记录理由。

| 类型 | 候选文件（相对于 `F:\道教\六爻`） | 试点目的 |
| --- | --- | --- |
| TXT 1 | `五行所属行业/六爻取用神之辩证看法.txt` | 与现有取用神试点对齐，复核原件到 Wiki 的链条 |
| TXT 2 | `《周易预测学》讲义..txt` | 检查编码、章节切分及梅花易数/六爻方法边界 |
| DOCX | `五行所属行业/六爻爻象详解.docx` | 检查段落、表格和嵌图的顺序及保留情况 |
| 旧 DOC | `六爻用神答疑（51页）王虎应.top.doc` | 检查旧格式转换，并与取用神 TXT 寻找可比观点 |
| 文字 PDF | `邵伟华周易预测学(下)  ..pdf` | 检查文字层、页码、阅读顺序；抽查后确认主题是否适合 |
| 扫描 PDF | `张成达八字六爻风水31册/11、张成达-六爻快速断卦法.pdf` | 用短篇测试中文 OCR、卦象及图表处理 |

TXT、DOCX、旧 DOC 样本原则上处理全文；如果发现损坏、加密或版面异常，应记录具体障碍和已处理范围，换一份同类文件完成可用样本。PDF 可以只处理**明确标注的连续章节或页段**；扫描 PDF 至少处理 3 页，候选短篇适合尝试全文。未处理页不能显示为已收录，更不能被 Wiki 引用。原件仍整份复制进项目。PPT、RAR、其余 130 多份文件不在本阶段批量转换范围。

## 3. 目录和交付物

```text
corpus/originals/     # 与 F 盘对应的原件副本，按相对路径保留目录
corpus/extracted/     # 机器提取/OCR 的忠实文本，保留页/段定位与疑点
corpus/cleaned/       # UTF-8 Markdown；只作可读性清洗，不伪造缺字
corpus/assets/        # 引用到的必要图片、卦象、表格或原页局部图
corpus/reports/       # 每份来源的质量、覆盖范围、问题和人工抽查记录
corpus/manifest.jsonl # 一行一个来源的机器可读登记
wiki/sources/         # 每个可用样本的来源页
wiki/concepts/        # 有出处的术语或问题页
wiki/comparisons/     # 有真实共同主题时的跨来源对照页
tools/                # 可重复执行的导入、转换、校验命令
```

开发方提交可重复执行的 Node.js/TypeScript CLI，负责登记、复制、哈希、调度格式转换、生成记录和检查链接。旧 DOC 与扫描 PDF 可调用离线安装的 LibreOffice、OCR 或 PDF 工具，但必须写明工具、版本、安装和重跑方式；这些**不成为生产聊天服务的必需依赖**。不能依赖 Codex 内置环境。转换程序不能直接把未经复核的机器摘要写成已核准的 Wiki 规则。

现有 `wiki/sources/src-08862b06aea9.md` 记录的是尚未导入的试点来源；本阶段应补齐它对应的包内原件、清洗文本和 manifest 记录，并更新状态。保留原有来源 ID；若哈希前缀碰撞，扩展新 ID 长度并记录映射。项目中其他已修改文件先检查再编辑，不覆盖阶段 1 的成果。

## 4. 来源登记与定位契约

`manifest.jsonl` 每行至少具备下列语义字段；具体命名可统一为 camelCase 或 snake_case，交付说明给出真实样例。

| 字段组 | 必需内容 |
| --- | --- |
| 身份 | 稳定 `source_id`、完整 `sha256`、原文件字节数、实际格式、扩展名、发现时间 |
| 路径 | 导入时的 F 盘相对路径、项目内原件相对路径；所有**运行时**输出路径均为项目相对路径 |
| 处理 | 输入编码或 OCR 语言、提取器/版本、处理时间、提取文本路径、清洗文本路径、相关图片路径 |
| 覆盖与质量 | 原件页数或结构概况、已处理页/章节、未处理范围、`usable` / `needs_review` / `failed`、疑点及逐页/逐段问题 |
| 关系 | 完全重复文件的别名路径、疑似同书不同版本的待核实关系；不能因文件名相似就合并 |

原件从 F 盘**只读复制**，复制前后核对 SHA-256。处理仅针对项目内副本。相同哈希只转换一次，重复路径作为别名记录；不同哈希即使同名也保留独立来源。导入后在另一台机器上只依赖项目目录即可打开、定位和校验已收录内容；F 盘绝对路径只允许作为审计历史，不得出现在运行时代码、链接或必需配置中。

原件到 Wiki 的链条必须是：`Wiki 主张 → source_id + locator → cleaned 段落/页 → extracted 对应位置 → originals 原件`。PDF 使用**PDF 实际页码**，印刷页码可另记；TXT/DOCX/DOC 用稳定的章节或段落编号，并可附起始语帮助人工查找。定位 ID 在重复转换同一原件时要稳定。没有可靠定位的句子只能标记「不可精确定位」，不得虚构页码。

## 5. 提取、清洗与图片规则

1. **保留两层文本。** `extracted` 忠实记录机器所见及页/段边界；`cleaned` 只做编码、换行、标题层级、重复页眉等可解释的清洗。删掉广告、转载说明、水印或疑似正文时，在质量报告中列出决定；有歧义就保留并标记。
2. **逐格式处理。** TXT 验证 UTF-8/GB18030 等实际编码；DOCX 检查段落、表格、图片或文本框遗漏；旧 DOC 先识别真实签名再转换；PDF 检查文字层是否只是水印及提取顺序；扫描页标记 OCR 语言、页码及低置信区域。失败不能返回空白的“成功文件”。
3. **图片进 Markdown，但不只留图片。** 对影响理解的卦图、表格、爻位等保留原貌或可定位的局部图，用项目相对路径引用，并写明来源 ID、原页/位置和说明；可辨认的信息同步转写为文本或结构化表格。看不清的字符和爻位标为未辨认，不能猜补。普通装饰图无需全部导出。
4. **清洗不等于可信。** 自动识别的作者、古籍引文、流派归属、预测案例和现实结果均保留“来源自述/待核实”的属性。不得把转载讲义的转引当作已亲自核对的古书原文。
5. **禁止外泄。** 默认本地离线 OCR，不把整本书发送到模型 API；若个别疑难页拟使用云端 OCR，先在交付报告中说明范围、成本和隐私影响，未获同意不调用。

## 6. 质量报告与准入门槛

每份样本报告至少列出：样本为何入选、页/段总量与已处理范围、工具及版本、编码/OCR 情况、开头/中部/结尾或所选连续区间的人工目视抽查记录、乱码/缺页/错序/图表损失、清洗改动、当前状态和后续处理建议。对 PDF，明确“整本已处理”或“仅第 X–Y 页”；对未处理页不进行质量背书。

质量状态定义：

- `usable`：在声明的覆盖范围内，关键术语、规则和所引段落经原件对照，定位可靠，可进入 Wiki；这不表示预测正确。
- `needs_review`：可阅读但仍有影响释义的 OCR、缺页、作者、版本或方法归属疑点；可建来源页说明情况，**疑点段落不能作为默认规则**。
- `failed`：无法提取或无法定位；只保留原件、错误和重试信息，不编入概念/对照页。

人工抽查是开发方对有限样本的核验工作，报告要指出由谁/什么方式核对、抽了哪些页或段、发现什么；不得写成“用户已审核”。没有现成标注集时不要虚报 OCR 准确率百分比。高风险的爻位、卦象、否定词、条件句和表格至少逐处对照原页，核对不完就保持待复核。

## 7. Wiki 内容要求

先建来源页，再把来源中的**明确主张**编入概念/对照页。至少交付 6 个来源页、1 个有两份以上来源的概念页、1 个围绕同一问题的来源对照页；如果候选文件缺乏真正可比主题，应换样本，不凑出表面比较。更新 `wiki/index.md`、`wiki/log.md`，为每页标明覆盖范围和维护状态。

每条可引用主张按 [Wiki 编写规则](../wiki/schema.md)记录 `source_id`、定位、来源观点、方法标签或“待确认”、适用条件或“未知”、整理状态与疑点。不同书或不同方法说法冲突时并列展示，并解释冲突来自术语、起卦输入、判读条件还是来源不清；没有证据就标记原因待查。`cross_checked` 只表示主张被另一份独立来源或原始引文核过，不表示占断已经证实。不要按来源数量投票得出“正统算法”。

Wiki 页面之间和到 `corpus/` 的所有链接必须是包内相对路径，可在移动项目目录后打开。阶段 4 的 Agent 将依据索引和这些页面选择材料，因此标题、主题标签、方法标签和覆盖范围要让人和程序都能读懂；不要求本阶段搭建搜索服务。

## 8. 安全、版权与打包

项目仅供用户私人部署。资料可能有第三方版权；登记作品名、文件自述的作者/版本及来源不明处，不把“持有电子文件”写成可公开分发许可。本阶段不要增加面向公网下载原件或整书的 API。工具运行时不得读取聊天数据库或上传私人会话。

大文件可不纳入 Git，但**发布/交接包必须显式包含**本阶段原件、产物、图片、manifest 和 Wiki；仅提供代码仓库克隆结果不算资料交付。交接说明给出文件清单、总字节数、哈希检查方法和在不同盘符或目录下重跑链接/来源校验的步骤。密钥、个人聊天记录、临时 OCR 缓存不进入资料包。

## 9. 开发方提交物与验收场景

提交：处理 CLI 与锁定依赖、至少 6 份原件副本、manifest、提取和清洗文本、所需图片、逐份质量报告、Wiki 页面/索引/维护日志、格式工具安装与重跑说明、样本更换及质量取舍记录。说明哪些文件或页已经可用、哪些仍需复核，不能用“资料已全部导入”概括小样本。

验收时由产品/架构方按交付内容抽查，至少覆盖：

1. 从两条 Wiki 主张分别沿 `source_id` 和定位找到清洗文本、提取文本及**项目内**原件；一条应来自 OCR 或 PDF。
2. 核对 6 个不同哈希与 5 类格式覆盖；TXT/DOCX/DOC 的全文或有据可查的例外，以及 PDF 的已处理页段与未处理页段。
3. 随机比对复制原件与 F 盘 SHA-256；确认 F 盘原件时间、大小和哈希未因处理而变化。
4. 查看一处图/表/爻位：Markdown 相对图片链接有效，文字记录与原页相符；模糊部分有明确标记。
5. 复跑导入不产生重复来源或覆盖人工 Wiki 内容；同哈希别名与不同哈希近名文件处理正确。
6. 模拟转换失败或低质 OCR：manifest/report 如实显示 `failed` 或 `needs_review`，不会自动进入可用规则。
7. 查看对照页：各观点能各自回到原文，方法差异和未核实点没有被合并成统一规则。
8. 复制完整项目资料到不带 F 盘路径的新目录，只用包内相对路径打开 Wiki 图片与出处并完成校验。

本阶段验收通过只证明**小样本资料可追溯、处理质量被如实报告**；不证明整库完成、Agent 已使用 Wiki、排盘正确或占断有效。下一阶段才审查第三方 Skill 与排盘算法。
