请在 `E:\workspace-ai\xuanxue\liuyao` 项目实施[第五阶段研发任务书](phase5_development_spec.md)。先阅读[第四阶段独立最终验收](phase4_final_acceptance_d6c5148_2026-10-09.md)、[阶段 4 交付说明](phase4_delivery.md)、[发布目录旧约定](../deploy/README.md)、[资料交付说明](phase2_delivery.md)与当前代码；以实际仓库状态为准。用户已确认目标为 **Linux + Docker**。产品/架构方负责独立签收，你负责设计、实现、自测与交付。

目标是交付**一套可离线转移的私有 Docker 发布包**，包含应用、六份已纳入来源链的资料、Wiki、页图、排盘运行代码、Compose 与说明；聊天数据库、备份、日志和密钥存于服务器独立持久化位置。先提交简短的 `docs/phase5_release_design.md`，明确目标架构、镜像内容白名单、存储挂载、密钥注入、代理链路、构建策略、发布清单、升级与回滚，再开发构建和验证脚本。

请重点完成以下事项：

1. 在与目标 CPU 架构一致的 Linux 镜像中构建/安装，实际验证 `better-sqlite3` 可加载；不要复制 Windows `node_modules` 或构建产物。用锁文件固定生产依赖。镜像导入服务器后不依赖 Git、npm 下载或开发机盘符。
2. 显式纳入被 Git 忽略的 `corpus/originals/` 六份原件，并校验 manifest、Wiki 目录、页图与定位；只纳入生产实际采用的 Skill/排盘文件及必要许可，不把四个外部仓库和审查缓存全打进去。
3. 逐项审查最终镜像和镜像层，解释第四阶段 `next build` 的动态追踪提示；证明 `storage/`、`.env.local`、真实密钥、测试临时数据和旧归档不在包里，同时证明运行所需资料未丢。记录源码提交、目标架构、镜像/归档哈希和逐文件清单，避免归档哈希自引用。
4. Compose 保持**单实例**，数据卷独立、容器非 root、宿主机应用端口仅绑定 `127.0.0.1`；容器内监听地址须适合 Docker 转发。反向代理用 HTTPS，核对 Cookie 与 SSE 首段及时到达；假模型不能在生产启用。
5. 提供升级前备份、旧库副本迁移、正式切换、隔离恢复演练和回滚流程。验证旧消息标题、来源摘录/页哈希、盘面快照与模型记录保留。不要对正式库做破坏性演练，不要用删除数据卷作为更新步骤。
6. 从**实际发布包**导入镜像并在隔离 Linux Docker 环境复验；开发目录的 `check:all` 只能作为补充。目标服务器未提供时把“包内复验通过”和“服务器部署待验收”分开写。真实 API 测试只在有服务器侧密钥时做最小调用，记录是否调用，不输出密钥。
