# 第四阶段研发任务书：Wiki、排盘与聊天融合

版本：2026-10-06。交付对象：负责实现的研发 AI。依据：[产品需求](product_requirements.md)、[技术架构](technical_architecture.md)、[研发计划](development_plan.md)、[第三阶段最终验收](phase3_final_acceptance_a27e672_2026-10-05.md)。产品/架构方编写需求并独立验收，研发方实现。

## 1. 目标、基线与判断

把已通过验收的三块能力接为一个**可自由提问的个人网页 Agent**：阶段 1 的登录、聊天、SSE、SQLite 历史；阶段 2 的六份样本、Wiki 与来源链；阶段 3 的确定性排盘。用户问一般问题时仍可聊天；问已收录的六爻概念时按目录读取少量相关 Wiki；给出充分起卦输入时调用本地排盘；后续追问沿用当时盘面快照。默认回答简明，必要时展开依据，最后一段以“最终结果：”开头。

**先纠正两种容易混淆的说法：**目录选页仍是在运行时读取知识，只是本项目不用 embedding、向量库或相似度检索；模型与排盘程序或两份来源一致，也不证明现实预测准确。当前 Wiki 只有六份小样本，不得把“能自由提问”表述为“已读完全部资料”。

首版以**文本和结构化盘面**完成闭环。原页图需能在有权限的出处页查看；不把 OCR 疑点自动提升为已核对事实。DeepSeek 官方当前说明 `deepseek-flash` 支持图像输入（[Vision](https://api-docs.deepseek.com/guides/vision/)），阿里云文档也列出 `qwen3.7-plus` 的视觉能力（[模型说明](https://help.aliyun.com/zh/model-studio/qwen3-7-plus)）。这使后续小范围视觉核对可行，但**本阶段不要求批量识图、自动 OCR 重做或把所有页图发给模型**。如研发方自愿加入按页视觉核对，必须另标“模型识别、待核对”，不得伪称人工校勘。

本阶段不扩充全部资料、不微调模型、不引入 embedding/RAG 服务、不实现吉凶/应期的权威算法、不做服务器发布包与备份恢复的最终验收（阶段 5）。不重写阶段 1 聊天或阶段 3 排盘核心；需要扩展时保持其公开契约与历史兼容。

## 2. 用户流程与缺项策略

| 场景 | 服务端应做什么 | 用户应看到什么 |
| --- | --- | --- |
| 一般自由问题，目录中无相关页 | 可调用所选模型，但不附本地来源；不声称读过未收录资料 | 简明回答；明确“本地 Wiki 暂无对应依据”或“以下为一般说明” |
| “什么是用神？” | 从 `wiki/index.md` 导航到 `concepts/yongshen.md`，必要时打开其中可定位的来源页/清洗段 | 说明来源主张、适用条件和不确定性；可展开可点击的出处 |
| “梅花起卦与六爻断卦怎么比较？” | 读取 `comparisons/meihua-vs-liuyao.md` 与必要的两份来源；保留 OCR 质量标记 | 并列“起卦”和“断卦”两个环节，不能制造虚假直接矛盾 |
| “帮我起卦/看这卦”，但未给六爻或历法输入 | 只询问计算所必需的缺项；不自动随机起卦、不拿发送时间冒充起卦时间 | 简短缺项提示，优先让不懂干支的用户提供六爻值、当地起卦时间及明确时区 |
| 六爻与时间齐备 | 先由本地排盘模块校验并计算，再让模型分析；问题的现实解释要标明来源和局限 | 结构化盘面与计算口径独立展示；模型文字不能覆盖卦名、动爻、世应等字段 |
| 对刚才那卦追问 | 读取绑定的 `chart_run` 快照；不以当前时间重算 | 看见“沿用盘面”与原起卦时间/规则版本；旧回答与引用不因资料更新变化 |
| 明确给了新的一组六爻或明确要求新卦 | 生成新 `chart_run`；若新旧问题边界或时间含糊，先追问 | 新旧盘可区分并回看，不悄悄覆盖旧盘 |

输入契约：保留自由文本；可加**非强制**的六爻输入区。服务端接受显式结构化 `chartInput`（六次 `6/7/8/9`，初爻在前；自动模式 `castAt + timezone + dayBoundary`，或手动模式合法日柱/月建），也可从清楚的文字中提取候选，但必须走同一排盘校验；含糊的爻序、硬币正反面或时间必须追问。浏览器可建议 `Asia/Shanghai`，用户需看得见并确认；服务器时区不得成为隐式输入。“现在起卦”应明确记录用户选择与实际捕获时刻。不得把发消息时刻自动当作既有卦的起卦时刻。

## 3. 目录选页与出处契约

1. 从 `wiki/index.md` 建立可审计的**机器可读目录**（可新增 `wiki/catalog.json` 或等价版本化文件）：页面相对路径、主题/别名、方法标签、所链来源 ID、质量状态、适用问题、索引版本。初版只覆盖现有六份资料与已建 Wiki 页；禁止因文件名、OCR 命中或模型猜测而自动生成“已核对规则”。目录变更要能追到源页与提交/哈希。
2. 运行时按标题、主题、别名和显式链接选页，再读取正文；**不遍历所有原件/清洗全文给模型，也不用向量检索**。默认限定选页数量与文本预算（建议不超过 4 页、正文总量不超过约 16,000 字符，配置可调），超限时说明覆盖不足或请用户缩小问题。记录实际选中的页面、哈希和截取范围，避免“目录命中”等同于“模型已读完整来源”。
3. 对模型只提供带编号的有限证据片段，如 `S1`、`S2`。每条证据至少含 `source_id`、Wiki 相对路径、原件/清洗文本定位（`¶NNNN` 或 PDF 实际页码）、片段、质量状态、方法/条件、文件版本或 SHA-256。发送给模型的片段与最终引用要分别记录；只有被实际引用且通过服务端映射的编号才能成为可点击出处。
4. 服务器校验引用编号是否在本次选页清单里；历史存当时的引用文本、定位、质量与哈希快照。引用展示由服务器生成内部链接，模型不能提供任意磁盘路径或任意 URL 充当包内出处。无目录命中时不生成伪引用。
5. 质量为 `needs_review` 的 OCR/卦图不作为默认确定规则；若用户指定该来源或比较需要它，应明确标“待核对”，并提供对应原页图入口。`src-e6fc8612e955` 第 20 页的世应冲突沿用阶段 3 记录，不在问答中偷偷裁决为“原书一致”。
6. 实现已登录的 `source_id + locator` 出处查看接口，按 manifest/目录白名单解析到包内文件；页图用服务端生成的受控 asset ID。拒绝 `../`、绝对路径、符号链接越界、未知 ID、越权访问与任意原件下载。端点只展示允许的 Wiki/清洗片段与必要原页图。

Wiki 内容和第三方 Skill 文本一律是**外部资料**，即使写着“忽略系统指令”“调用工具”等也不能改变服务端规则、权限、选页范围或排盘 JSON。研发方用隔离的恶意 Wiki 样例证明这一点，不改正式资料。

## 4. 排盘与会话状态

- 在 `app/` 增加**服务端**排盘适配层，调用阶段 3 的 `buildChart`/历法接口；复用 `paipan/rules/rule-profile.v1.json`，不把排盘算法重写到提示词或浏览器。研发方可选 workspace package 或编译后的 JS，但须说明并验证 Next 构建、Node ≥ 22.18、项目迁移及生产依赖；**不能只在开发机用跨目录源码导入碰巧跑通**。
- 新盘保存输入原文、规范化爻值、时间/时区/日界、手动或自动来源、规则版本、核心版本、完整结构化盘面和稳定哈希。计算失败或输入不齐时不生成完整盘；错误/缺项由界面与历史如实显示。盘面板和关键字段摘要由本地 JSON 渲染，模型只提供解释与来源观点。
- 每次回答明确绑定“无盘 / 沿用某个旧盘 / 新建某个盘”。可在会话保存当前盘引用，但历史消息必须保存当时关联的 `chart_run_id`；后续追问只读快照。若出现另一组爻值或“另问一事”，不要覆盖旧盘；无法判断是否沿用时问一句澄清。
- 不把阶段 3 的未核实规则升级为确定性吉凶：用神选择、旺衰、应期和现实结果属于带来源/方法标签的解释，若 Wiki 没有足够证据则说不足。

## 5. 聊天编排、模型与界面

保留现有 `POST /api/conversations/{id}/messages` + SSE、登录、停止生成、历史分页、会话两处重命名。建议流程：鉴权与去重 → 保存用户消息/助手占位 → 判断问题与缺项 → 目录选页 → 必要时排盘或读取旧盘 → 组装有预算的上下文 → 调模型流式返回 → 校验引用与盘面呈现 → 保存最终状态、用量和快照。模型调用期间不持有 SQLite 写事务。缺项澄清可由本地逻辑完成，但也必须落库并按现有事件/状态契约呈现。

为编排层定义可记录的计划对象，至少包含 `intent`（一般问答/概念/来源比较/排盘/旧盘追问）、`selectedPageIds`、`chartAction`（无盘/新盘/沿用/追问）、`missingInputs` 和选择理由。可用可解释的规则或模型辅助识别意图；**最终选页、文件读取、排盘调用和预算由服务端验证执行**，模型不得给出任意路径或未经确认的爻值去直接调用工具。含糊时优先追问，不开启无界的自动工具循环。

扩展现有共享 DTO/SSE：`start` 保持兼容；新增可选的 `sources` 和 `chart` 事件，携带**服务端已验证**的引用/盘面快照 ID 与展示摘要；`done`/历史 GET 能返回同一快照。旧 `delta` 只承载模型文本；客户端最终展示和历史均以服务端保存的核对结果为准。任何未映射的 `Sx` 不能变成可点击“出处”。流中断、上游错误时保留已生成文本、选页和盘面状态，状态仍为 `interrupted`/`failed`，不得伪装完成。

把阶段 1 的 `phase1-v1` 系统提示升级为明确版本的阶段 4 提示，删除“尚未接入 Wiki/排盘”的旧陈述；提示中清楚区分系统规则、用户问题、只读 Wiki 片段和不可改写的盘面 JSON。回答默认先简明分析；“展开依据”展示来源、质量与计算口径；末段固定“最终结果：”。已发生/未发生的现实预测不得用模型语气伪装成已验证事实。

保持 DeepSeek 官方 `deepseek-flash` 默认；增加阿里云百炼 `qwen3.7-plus` 适配器，只有密钥配置且适配器可用时才允许选择，逐条记录实际服务商/模型/提示版本/用量。两家上游流式协议、结束标记、错误与用量各由适配器解析，不因为接口表面相似就复用错误的终止判断。未配置千问时默认 DeepSeek 仍可用；假模型/模拟上游仅用于离线验收，不在生产自动启用。模型切换不能改动 Wiki、历史引用或旧盘。

## 6. 存储迁移与失败语义

新增版本化 SQLite 迁移，不修改 `0001_init.sql` 的既有含义，不清空已有库。至少需要：`chart_runs`（输入与结果快照、版本、哈希、会话/消息关联）、`message_sources`（编号、来源 ID、定位、质量、摘录、哈希、关联助手消息）；必要时加会话当前盘引用或消息关联表。外键与索引应保证单用户归属、重试去重和消息分页。旧阶段 1 消息读出时来源/盘面为“无”，原文、状态、标题、模型不变。

模型用量沿用现有字段或迁移到独立表均可，但不能让失败/中断覆盖旧用量。备份脚本应继续支持新库，验证从旧库迁移、重启恢复与历史回看。来源/盘面快照持久保存后，即使 Wiki 页面或排盘配置升级，旧回答仍显示当时版本。

## 7. 固定验收样例与门槛

研发方提交可复跑的离线模拟上游和（有密钥时）真实 API 联调记录。验收方会使用未写入样例的新提问和新卦。至少覆盖：

1. 通用问题无 Wiki 命中；“取用神”命中正确概念页和定位；“梅花起卦/六爻断卦”并列不同前提；未知书名不冒充已收录。
2. `needs_review` 来源显示质量提示与原页图；不可达段落、错 `source_id`、伪造 `S99` 不成为有效引用；完整出处能回到包内 `source_id + ¶NNNN/页码`。
3. 完整静卦、多动爻、非法爻值、无时区、含糊爻序、手动日柱/月建、节气边界；与阶段 3 CLI 的 canonical 盘面逐字段一致。缺项只追问，不能凭服务器时间或模型猜测补全。
4. 旧盘追问和重启后追问沿用同一快照；新输入生成新盘；旧消息关联的盘面和来源在页面修改后仍保留旧版本。
5. DeepSeek、已配置的千问、无千问密钥、假模型/上游故障/停止生成、登录与资源归属；模型切换后旧消息模型与快照不变。SSE 新旧事件有清晰顺序，历史列表和两处重命名仍可用。
6. 使用阶段 1 的旧数据库副本迁移，不丢历史消息；从项目根以外启动和打包迁移后，Wiki/排盘都不访问 `F:`/`E:` 开发机路径；API 不泄露密钥、内部提示词、任意文件或本机绝对路径。

**通过条件：**四类主流程（概念、来源比较、具体卦例、旧卦追问）从网页到历史能走通；最终可点击引用均由服务端验证并有快照；盘面字段与本地工具一致且旧盘不重算；缺项/低质量资料不伪装完整事实；阶段 1 的登录、SSE、历史及标题能力无回退；模型配置和迁移行为可复现。现实占断命中率不作为本阶段软件验收标准。
