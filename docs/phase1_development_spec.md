# 第一阶段研发任务书：可持久保存的自由聊天网站

版本：2026-10-01。交付对象：负责编码的开发 AI。本任务书细化 [研发计划](development_plan.md) 的阶段 1；[产品需求](product_requirements.md) 与 [技术架构](technical_architecture.md) 是上位约束，[验收清单](acceptance_checklist.md) 用于最终首版验收。产品/架构方负责复核交付，不承担本阶段编码。

## 1. 本阶段要交付什么

用户打开一个需要登录的网页，可以自由输入问题，与 DeepSeek Flash 流式聊天；左侧能查看和继续历史会话。**当前聊天页顶部和历史列表都能手动重命名同一会话标题。**聊天、标题及生成状态保存在服务器，刷新网页或重启服务后仍在。这是后续接入 Wiki、排盘和其他模型的基础闭环。

本阶段只连接 DeepSeek 官方 API。当前 Wiki 只有试点内容，排盘算法尚未接入；网页与回答不能暗示已经读取全部六爻书籍或能够计算具体卦盘。具体六爻排盘问题可以解释缺少的能力和输入，但不得编造盘面、来源或“已核对”的结论。用户已确认重命名对象是**当前和历史会话的标题**，不是输入框提示语。

## 2. 固定技术选择

| 层 | 要求 |
| --- | --- |
| 语言与网站 | Node.js 当前受支持的 LTS 版本、TypeScript、Next.js App Router；自托管 Node 运行时，不做纯静态导出 |
| 模型接口 | 服务端调用 DeepSeek 官方 API 的 `deepseek-flash`；阶段 1 固定使用 Chat Completions 流式接口，`stream: true`；将上游增量转换为本项目自己的事件格式。官方[对话补全文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)说明其 SSE 增量与最终用量字段 |
| 浏览器流 | `fetch()` 发送 `POST` 请求并读取 `text/event-stream`；无需 WebSocket。历史列表和重命名使用普通 JSON 接口。[Next.js Route Handler](https://nextjs.org/docs/app/api-reference/file-conventions/route)支持 `POST` 与流式响应 |
| 数据库 | SQLite + `better-sqlite3`，版本化 SQL 迁移；数据库位于项目持久化 `storage/`。单用户单实例，不要求 PostgreSQL。[驱动说明](https://github.com/WiseLibs/better-sqlite3) |
| 登录 | 一个拥有者账户；密码保存强哈希，服务端会话以安全 Cookie 维护；所有聊天接口要求登录 |
| 目录 | 应用代码放项目 `app/`，运行时数据放 `storage/`；为后续 `wiki/`、`corpus/`、`skills/` 保留服务端接口边界，但本阶段不加载其内容作为已核准知识 |

依赖版本须锁定。服务端密钥由环境变量提供，浏览器包、数据库、Git 和发布包不得包含真实 API Key。Windows 开发产生的 `node_modules` 不复制到 Linux 服务器；服务器按锁文件构建。

## 3. 页面行为

### 3.1 页面布局

- 左侧：新建聊天按钮、按最近活动排序的历史会话、每条会话的标题与重命名入口。
- 主区顶部：当前会话标题与重命名入口；改名后左侧对应历史项同步更新。
- 主区消息列表：区分用户与助手；正在生成时逐步显示文字，完成后显示最终内容；错误和中断有清晰状态。
- 底部：多行文本输入框、发送按钮、生成中的停止按钮。Enter 发送、Shift+Enter 换行；空白消息不可发送。
- 小屏幕可打开和关闭历史列表；刷新或切换会话后不丢失已保存的消息。
- 助手内容可以安全渲染 Markdown；不执行模型返回的 HTML、脚本或任意链接命令。

### 3.2 会话规则

1. 点击“新建聊天”先进入空白草稿；发送第一条消息时才在服务端创建会话，避免空历史项。
2. 首条消息成功保存后，用其开头生成简短默认标题，不额外调用 LLM。用户可从当前聊天页顶部或历史列表改名；两处均调用同一更新接口并同步显示。手动重命名后标记为 `manual`，后续消息不能自动覆盖。
3. 历史列表按 `updated_at` 降序展示；重新打开会话能看到已保存消息，并在同一会话继续提问。
4. 同一会话同一时间只允许一个进行中的模型请求。用户点击停止后，本条助手消息标为 `interrupted`，保留已收到的部分内容。
5. 网络失败、模型限流或服务重启时，应显示可理解的错误或中断状态；重新发送不应静默生成重复的用户消息。
6. 历史长期保留在数据库，发送给模型的上下文采用可配置的最近消息预算。**历史保存量与单次请求上下文量是两件事。**

本阶段仅显示 DeepSeek Flash 为已接入模型；千问选择入口在阶段 4 接通 API 后启用。历史回复保存当时的实际模型名称。

## 4. 服务端接口契约

所有正文为 UTF-8；普通接口返回 JSON。路径中的 `{id}` 为不可预测的会话 ID。所有会话接口均检查登录状态和记录归属。

| 方法与路径 | 输入与输出 | 核心约束 |
| --- | --- | --- |
| `POST /api/auth/login` | 密码 → 安全会话 Cookie | 失败不泄露密码、哈希或账户存在细节；限制频繁尝试 |
| `POST /api/auth/logout` | 清除当前会话 | 退出后历史接口不可访问 |
| `GET /api/auth/me` | 当前登录状态 | 仅返回必要的拥有者信息 |
| `GET /api/conversations?cursor=&limit=` | 会话摘要分页 | 按 `updated_at` 倒序；不返回空草稿 |
| `POST /api/conversations` | `{clientConversationId}` → `{id, title, createdAt}` | 首条发送时调用；客户端固定一个草稿 ID，重试时不能创建重复会话 |
| `GET /api/conversations/{id}` | 会话元数据 | 不把整个长期历史一次性发给浏览器 |
| `GET /api/conversations/{id}/messages?before=&limit=` | 消息分页 | 顺序稳定，包含 `streaming/completed/interrupted/failed` 状态 |
| `PATCH /api/conversations/{id}` | `{title}` → 更新后的标题 | 当前页与历史列表共用；去首尾空白、限制长度；写入 `title_source=manual` |
| `POST /api/conversations/{id}/messages` | `{clientMessageId, content}` → SSE 流 | 消息 ID 由客户端生成用于去重；服务端先存用户消息再调模型 |
| `GET /api/healthz` | 基础存活状态 | 不暴露密钥、路径或数据库内容 |

开发方可调整字段的命名风格，但交付说明必须列出最终请求/响应示例，前端与后端共享类型定义。权限失败、输入错误和并发冲突分别返回明确状态码；请求已经开始流式返回后，错误改用流事件表达。

### 4.1 SSE 事件

服务端对浏览器输出标准 `text/event-stream`，事件数据是 JSON。至少定义：

```text
event: start
data: {"conversationId":"...","userMessageId":"...","assistantMessageId":"...","model":"deepseek-flash"}

event: delta
data: {"text":"新增文本"}

event: done
data: {"assistantMessageId":"...","status":"completed","usage":{"inputTokens":123,"outputTokens":45}}
```

生成失败时发送 `event: error`，包含安全的错误码、简短说明及消息 ID，然后关闭流；用户主动停止或连接断开时记录 `interrupted`。可使用 SSE 注释作保活。浏览器解析增量事件时需处理 UTF-8 字符被网络分块切开的情况。上游 DeepSeek 事件不能原样透传给页面：由服务端统一转换格式，后续接入千问时页面协议保持不变。

服务端响应应设置不缓存，并按目标代理配置关闭缓冲。开发方须确认在实际部署路径中，第一段内容会在模型全部完成之前到达浏览器。[Next.js 自托管流式说明](https://nextjs.org/docs/app/guides/self-hosting)

### 4.2 消息保存时序

1. 验证身份、输入、`clientMessageId`、会话归属和当前是否已有生成任务。
2. 在短事务内保存用户消息及助手占位消息 `streaming`；释放事务后再请求 DeepSeek。重复的 `clientMessageId` 不得插入第二条相同用户消息。
3. 边接收上游增量边推送给浏览器，同时定期把已生成文本写入数据库，以便进程异常时保留最近的内容；不把密钥和原始上游请求写入日志。
4. 正常结束时保存最终文本、`completed`、模型和用量，再发送 `done`。失败/中断时保存已生成部分及状态，供历史恢复。
5. 进程异常重启后，遗留的 `streaming` 消息在恢复流程中标为 `interrupted`；不会永久显示“正在生成”。

API 限流、超时和网络断线的错误信息应对用户可理解，同时在服务端记录可排查的非敏感错误码。当前请求正在流式生成时不允许同一会话再发一条问题。

## 5. 持久化契约

最少包含以下数据，使用版本化迁移创建；字段名可由开发方统一风格，但语义不可丢失。

| 表 | 必需信息 |
| --- | --- |
| `conversations` | ID、客户端草稿 ID（创建去重）、拥有者 ID、标题、`title_source`（自动/手动）、创建与更新时间 |
| `messages` | ID、会话 ID、`client_message_id`（用户消息去重）、角色、正文、状态、模型名、提示版本、创建与完成时间、错误码、用量 |
| `sessions`（若采用服务端会话） | 会话标识、过期时间和撤销状态；不保存明文密码 |

聊天数据库存于 `storage/`，不得与只读 Wiki 混放。启用适合 SQLite 的事务与 WAL 配置，并实现安全备份方式。应用发布包可整体替换，但 `storage/` 必须以持久化卷或独立目录保留。阶段 1 交付文档须包含一次备份和恢复步骤。

时间戳以统一时区格式存储，页面按用户所在时区显示；标题排序、分页和历史恢复不能依赖客户端时钟。

## 6. DeepSeek 适配要求

- 由服务端读取 `DEEPSEEK_API_KEY`、API 地址和模型名；缺少密钥时展示明确的配置错误，不向浏览器返回密钥值。
- 阶段 1 使用 `deepseek-flash` 的 Chat Completions 流式接口，并请求可获取的用量信息。多轮上下文由本服务从数据库构建；单次发送的消息数量和长度应有可配置上限。[DeepSeek 官方接口文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)
- 服务端提示词固定本项目回答风格：简明、事实与推测分开、缺少证据时说明，最后写“最终结果”。阶段 1 不提供来源页或排盘结果时，不允许模型编造书籍页码或具体卦盘。
- 模型适配层对应用只暴露统一的“开始生成 / 文本增量 / 完成或失败 / 用量”接口，为阶段 4 接入千问留下位置。
- 不把整段长期历史、项目原件或当前未使用的 Wiki 自动发给 API。

## 7. 安全与部署约束

- 首版为单用户登录。密码仅存强哈希；Cookie 使用 `HttpOnly` 和合理的 `SameSite` 策略，HTTPS 环境使用 `Secure`。变更状态的接口要考虑跨站请求保护。
- 聊天消息有长度上限，历史接口分页；对模型返回内容做安全渲染，不执行任意 HTML 或脚本。
- API Key、密码、会话密钥均由环境或服务器密钥管理注入，不写入发布包、网页代码、数据库和调试日志。
- 自托管 Node 服务可以放在 HTTPS 反向代理后；代理需要透传长连接并关闭该聊天接口的响应缓冲。提供单实例启动方式与 `storage/` 持久化说明。

## 8. 开发方提交物与阶段验收

建议按以下依赖顺序交付：先完成项目启动、登录与数据库迁移；再完成会话和消息 API；随后接入 DeepSeek 流式适配器与中断状态；最后接网页交互、备份恢复及单实例部署。每一步都使用同一份数据模型和事件契约，避免前后端分别定义不兼容的消息结构。

提交物：源代码、依赖锁文件、数据库迁移、环境变量模板、启动/部署说明、备份恢复说明、接口及 SSE 事件示例、阶段 1 已知限制和验收证据。无需导入全部原始资料或安装四个外部仓库。

验收至少演示以下场景：登录 → 新建会话 → 流式问答 → 停止一次生成 → 再次发送并完成 → **从当前聊天页顶部改名，历史列表同步** → **从历史列表再次改名，当前页同步** → 刷新页面 → 重启服务 → 从历史打开并继续；另演示未登录访问被拒绝、缺少 API Key 的安全错误、网络/模型故障不会造成重复用户消息或永久 `streaming` 状态。产品/架构方会依据实际交付逐项记录通过与未通过，不以提交代码或自述测试通过替代验收。
