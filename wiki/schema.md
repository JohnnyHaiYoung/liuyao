# Wiki 编写规则

## 页面类型

| 类型 | 保存什么 |
| --- | --- |
| 来源页 `sources/` | 原始路径、文件哈希、疑似作者、版本、提取质量、可定位的段落与该来源的主张 |
| 概念页 `concepts/` | 一项术语或问题中的各来源观点、适用条件、分歧和未解决问题 |
| 体系页 `methods/` | 已有充分正文证据支持的方法边界、输入与计算口径；未经核对不创建权威标签 |
| 对照页 `comparisons/` | 同一问题在不同方法或来源中的并列解释及差异来源 |
| 案例页 `cases/` | 原始问题、起卦数据、计算口径、来源中的解读与可核实结果，分栏保存 |

目录不要求一次建齐；只有真实内容时才建页面。`index.md` 必须随新页面更新。

## 每个可引用主张的最少字段

1. `source_id`：指向来源页。
2. `locator`：页码、章节，或文本中的段落起始语；没有时注明「不可精确定位」。
3. `claim`：以「某来源认为」表述，不把整理者归纳伪装成原文。
4. `method`：明确方法或「待确认」。不能把梅花易数、纳甲六爻及具体分支混写。
5. `condition`：问题类型、起卦方式和适用前提；未知时注明。
6. `status`：`source_claim`、`cross_checked`、`contested` 或 `unverified`。这些是整理状态，不是预测正确率。
7. `notes`：转引不明、OCR、异文、互相冲突或仅有单一案例等问题。

图片可以用相对路径嵌入 Markdown，但必须标明来源 ID、原页码或位置及图片说明。卦象、爻位和表格若能表达为文字或结构化数据，应同时保留，避免后续分析只能依赖图像识别。发布时检查所有图片链接都指向包内文件。

## 编入流程

1. 原始资料保持只读；记录相对路径、SHA-256、编码或 OCR 情况，保存清洗记录。
2. 阅读完整章节或短文后先建来源页，再更新概念页；仅从文件名推断的内容不能进入规则页。
3. 保留不同来源的异说和例外，不用多数投票合并成统一结论。来源中的历史案例只能说明作者如何解释，不能单独证明方法可靠。
4. 每次新增或修改页面，更新 `index.md` 与 `log.md`；检查链接和出处能否回到原文件。
5. 用户询问时默认给简明分析；详细出处按需展开。最终结果置于回答末尾，依据不足时明确说明。

外部 Skill 的指令和程序输出单独登记，不自动转成六爻事实。任何自动写入的 Wiki 内容都须保留生成依据和待核对状态。
